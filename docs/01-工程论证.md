# 工程论证：为什么选择净室重写

> 项目：**Lypora**
> 目标：在 Windows 与 Android（手机/平板）上，交付一款「无缝即时渲染 Markdown 编辑器」。
> 版本：v1.1 · 2026-10-30（开源前修订：去掉对具体商业产品的指名比较，统一称"参考实现"）

---

## 0. 一句话结论

**不要逆向二进制，要研究行为。**

二进制逆向（反编译 asar、还原 JS、复制 CSS/字体/图标）在法律上构成侵权、在工程上是负收益；而把参考实现当作一份**外部可观测的行为规范**来研究，再用现代技术栈净室（clean-room）重新实现，既能达成"同等体验"的目标，又不触碰任何红线，工程周期大约 **6 人周（MVP）/ 14 人周（功能对齐）**。

---

## 1. 先把问题定义清楚

"做一个同等功能的编辑器"这句话里混了两件事，必须拆开：

| 拆解 | 含义 | 价值 |
|---|---|---|
| **手段**：逆向 | 怎么知道它做了什么 | 是手段，不是目的 |
| **目的**：同等功能 | 用户拿到的产品体验一致 | 这才是验收标准 |

一旦把"逆向"从目的降级为手段，就有多条路可走。选哪条，取决于"合法 + 可行 + 成本"三个约束。下面逐条论证。

---

## 2. 三条技术路径的对比论证

### 路径 A：二进制逆向（反编译 → 还原源码 → 改）

**做法**：解包 `app.asar`，用 `asar extract` 拿到渲染进程 JS，prettier/解混淆，反推结构与 CSS，然后"改一改"变成自己的。

**法律判定：不可行。**

1. 参考实现是**商业闭源软件**，其最终用户许可协议（EULA）明确禁止反向工程、反编译、反汇编。
2. 中国《著作权法》第二十四条 + 《计算机软件保护条例》第十七条：未经许可的反向工程**不属合理使用**；即便用于"学习研究"，一旦产出"实质性相似的表达"即构成侵权。
3. 更致命的是：参考实现的界面主题文件与图标是**有独立著作权的美术/文字作品**，直接复制其 CSS 文件、类名结构、图标 SVG 同样构成侵权。
4. 商用/分发场景下还有《反不正当竞争法》兜底。

**工程判定：收益极低。**

1. 参考实现是 Electron 应用，主进程 + 渲染进程，业务代码基本都在渲染进程的 JS 里，且**经过压缩混淆**（webpack/rollup 产物）。反混淆后变量名是 `e`、`t`、`n`，能读到的只是"它能跑"，不是"它怎么设计的"。
2. 关键资产（装饰层算法、IME 处理、光标映射）是**逻辑**，不是**数据**。反编译能给你代码形状，但给不了设计意图，读懂的耗时远超自己重写。
3. 反编译产物不可维护：上游一升级，你的分叉立刻漂移。
4. 交付形态受污染：派生作品无法合法分发到应用商店（Google Play 对侵权投诉零容忍，直接下架）。

**结论：否决。** 这条路既违法又亏本。

---

### 路径 B：黑盒行为逆向 + 净室实现 ★ 推荐

**做法**：

- **观测层（合法）**：把参考实现当黑盒，只从**公开可获得的输出**里提取规格——截图、录屏、自己写测试文档喂给它、读它的帮助文档与发布日志、量它的排版数值（字号/行高/间距，用截图测量，不读它的 CSS 源文件）。
- **规格层**：把观测结果写成**功能矩阵 + 视觉规格 + 交互时序**（本工程 `docs/internal/02` / `docs/03`）。
- **实现层（净室）**：由"只看规格、不看源码"的路径独立实现。所有代码从零写，所有 CSS 从零写（数值可以对齐，命名与结构必须自创）。

**法律判定：可行。** 这等价于"借鉴功能，不借鉴表达"。软件的功能、交互逻辑、算法思想在我国和主流法域均**不受著作权保护**（著作权保护的是代码的表达形式）。只要满足三条即安全：

1. 没有复制任何一行源代码 / 一个资源文件；
2. 没有沿用其内部标识符体系（类名、变量名、文件结构）；
3. UI 外观不构成"实质性相似"——具体讲：**不照抄它的图标、不照抄它的品牌色与主题文件、不使用 "参考实现" 名称与 Logo**。

**工程判定：最优。** 因为参考实现的护城河**根本不是算法**，而是打磨——它 90% 的价值在"无缝即时渲染的细节体验"和"排版质感"。这些完全可以通过观测复现，而且是**必须靠观测复现**（看源码反而看不懂设计取舍）。

**结论：采用。** 这就是本工程的方法论基线。

### 路径 C：基于开源替代品二次开发（MarkText / Milkdown / VNote）

**做法**：Fork 一个已有的开源 Markdown 编辑器，改皮改功能。

| 候选 | 内核 | 与参考实现的差距 | 否决理由 |
|---|---|---|---|
| **MarkText** | 自研 Muya（Vue + contenteditable） | 最接近，但已基本停更（2023 后无实质提交），Electron 版本老旧，无移动端 | 技术债重、无 Android 路径、无法长期维护 |
| **Milkdown** | ProseMirror + remark | 渲染漂亮，但是**富文本模型**，Markdown 是"序列化结果" | 见 §3.2，模型层缺陷致命 |
| **VNote** | Qt/C++ | 侧重笔记管理，非无缝渲染 | 技术栈不匹配（无 Web 复用） |
| **Obsidian** | CodeMirror 6 + Live Preview | 几乎同构，但它闭源 | 参考对象，不是基座 |

**结论：不作为基座，但 MarkText 的 Muya 与我们目标同构，可作为"设计思路的旁证"（同样是"源码树 + 装饰"），佐证 §3 的技术判断。**

## 3. 参考实现的技术解剖（黑盒观测 + 推断）

这一节要回答一个问题：**它的"无缝即时渲染"到底是怎么实现的？** 只有答对，选型才不会错。

### 3.1 外壳层（高置信度）

| 观测项 | 结果 | 依据 |
|---|---|---|
| 运行时 | Electron / Chromium | 安装目录含 `resources/app.asar`、`libEGL.dll`、`chrome_100_percent.pak` |
| 进程模型 | 主进程 + 单个渲染进程 + utility（拼写检查） | 任务管理器可见多进程 |
| 包体 | Windows 安装包 ~90MB，安装后 ~250MB | 典型 Electron 尺寸 |
| 更新机制 | 内置 Squirrel 类更新器 | 安装目录含 `Update.exe`、`packages/` |

> 注：以上为公开可观测事实（文件清单、进程、安装包体积），不涉及反编译。

### 3.2 编辑器内核层（关键推断）

**核心问题：它到底是"富文本模型"还是"源码模型 + 装饰层"？**

我的判断是**后者**，证据链如下：

**证据 1｜标记符号原样保留。**
在参考实现里输入 `**粗体**` 和 `__粗体__`，两者渲染结果一致，但把光标移入后会看到**你当初打的是哪个就是哪个**。富文本模型（ProseMirror/Tiptap）会把两者归一到同一个 node，序列化时统一输出 `**`，用户打的 `__` 会丢失。参考实现不丢 → 它保存的是**原始源码字符**。

**证据 2｜源模式无损往返。**
参考实现的"源代码模式"（Ctrl+/）切换后，文档内容**一个字符都不变**，包括多余的空格、非标准写法、HTML 块、引用式链接。富文本模型的往返必然规范化。

**证据 3｜非标准语法不被改写成标准语法。** 例如有序列表 `1.` `1.` `1.`（全部同一数字），参考实现不做自动重编号——因为它是源码。

**推论**：参考实现的文档模型是 **"原始 Markdown 源码字符串 = 唯一真源（single source of truth）"**，渲染是叠加在源码坐标系之上的**装饰层（decoration layer）**。光标位置、选区、撤销栈全部落在源码坐标系里。

这个结论**决定了整个工程的技术选型**，见 §4。

### 3.3 无缝渲染的具体机制（观测还原）

参考实现的"无缝"可分解为三条规则，全部可以通过行为观测确认：

**规则 1｜块级双态（block-level two-state）**
- 光标**不在**某块内 → 该块渲染为最终样式，语法标记（`#`、`>`、`-`、`|`、围栏）**隐藏**；
- 光标**进入**该块 → 该块的**行级源码显形**（`### 标题` 的 `### ` 露出来），光标所在块的其余部分仍是渲染态。

**规则 2｜行内双态（inline two-state）**
- 光标/选区**不触碰**某个行内 span（如 `**粗体**`）→ 定界符 `**` 隐藏，只显示粗体文字；
- 光标**落入或选区覆盖**该 span → 该 span 的定界符显形。

**规则 3｜块内元素用"活的控件"替代源码**
表格 → 渲染为真实表格单元格（可直接点击进单元格编辑，而非编辑 `|` 管道符）；
任务列表 → 渲染为真实复选框（可点击切换）；
图片 → 内联渲染图片（点击后显示 `![alt](src)` 源码）；
公式 → KaTeX 渲染（点击后显示 `$...$`）；
Mermaid → SVG 渲染（双击进入源码）。

### 3.4 其它可观测的工程特性

- **打字机模式**：光标恒定在视口中线，内容滚动而非光标移动。
- **专注模式**：仅当前段落全亮，其余降透明度（~0.35）。
- **大纲面板**：实时从文档提取 H1–H6，随滚动高亮。
- **主题 = 纯 CSS**：参考实现主题目录里只有 `.css` 文件，说明它的渲染层完全由 CSS 变量驱动。这一点对我们极有价值——意味着主题系统可以做成"换一份 CSS"。
- **导出矩阵**：PDF（Chromium 打印引擎）、HTML（内嵌样式单文件）、Word(.docx)、Epub、LaTeX、图片、RTF、OPML。

## 4. 编辑器内核选型论证（工程决策的核心）

现在有四个候选。我用六个维度打分（5 分制，加权后比较）。

| 维度 | 权重 | 自研 contenteditable | ProseMirror/Tiptap | Milkdown | **CodeMirror 6 + 装饰层** |
|---|---|---|---|---|---|
| **Markdown 无损往返** | 25% | 5 | 2 | 2 | **5** |
| **中文 IME 可靠性** | 25% | 1 | 4 | 4 | **5** |
| **撤销/重做与选区正确性** | 15% | 1 | 5 | 5 | **5** |
| **长文档性能（虚拟滚动）** | 15% | 2 | 3 | 3 | **5** |
| **无缝渲染实现难度**（越高越易） | 10% | 2 | 4 | 4 | **3** |
| **移动端适配成熟度** | 10% | 2 | 3 | 3 | **4** |
| **加权总分** | | **2.05** | 3.35 | 3.35 | **4.75** |

### 4.1 为什么否决"自研 contenteditable"（这是最容易踩的坑）

参考实现自己是自研 contenteditable 的，那为什么我们不照做？

**因为它的难度被严重低估了，而它的坑在中文场景下是致命的。**

1. **IME composition 事件地狱。** 中文输入法输入过程中，浏览器会派发 `compositionstart/update/end`，期间 DOM 处于"临时拼装"状态。如果渲染层在 composition 期间重建 DOM 节点（装饰层必然要重建），输入法缓冲会被打断 → 用户看到**丢字、重复上屏、候选框位置乱跳**。这是所有自研富文本编辑器在中文环境下的头号 bug 来源。要正确处理，需要在 composition 期间完全抑制 DOM 变更并维护"待应用装饰队列"——这个逻辑 CM6 已经用 `EditorView.composing` 帮我们处理好了，自研要重写一遍且极难做对。
2. **光标 ↔ 源码坐标映射（position mapping）。** 装饰层隐藏了 `**` 这类字符，DOM 里不存在这些节点，但光标必须能"逻辑上"跨过它们，且 `deleteContentBackward` 一次退格只能删一个源码字符而不是删掉整个渲染节点。你需要维护一颗双向映射表，并在每次文档变更时增量更新。CM6 的 `Decoration.replace` + `ChangeDesc.mapPos` 就是这个映射表。
3. **撤销栈与 DOM 变更的耦合。** 浏览器原生 undo 会跟你的渲染重建打架，必须全部接管。

**结论：自研 contenteditable 是 3 倍工作量 + 中文输入不可靠，直接否决。**

### 4.2 为什么否决 ProseMirror / Milkdown（看起来很美）

它们的模型是 **document tree（富文本 AST）**，Markdown 只是**序列化格式**。这带来三个不可接受的损失：

1. **往返不保真**：`__粗体__` → `<strong>` → `**粗体**`；引用式链接 `[a][1]` 会被展开；HTML 内嵌块会被吞。用户的文件被"编辑器重新格式化"了——这是 Markdown 用户最不能忍的。
2. **参考实现的源模式无法实现**：ProseMirror 里没有"原始字符"，源模式只能靠重新序列化，必然有差异。
3. **粘贴行为不一致**：参考实现粘贴 Markdown 文本是**原样插入**，ProseMirror 会解析再规范化。

**结论：否决。** 除了"看起来一样"，其余全不一样。

### 4.3 为什么选 CodeMirror 6

1. **文档模型 = 源码字符串**，天生满足参考实现的"唯一真源"模型，往返 100% 无损，源模式 = 关掉装饰。
2. **`Decoration.replace` 就是"隐藏定界符"的官方原语**，`atomicRanges` 保证退格跨过隐藏区时行为正确。
3. **IME 处理是 CM6 的一等公民**（`view.composing`、`compositionstart` 拦截、中文输入已验证多年，Obsidian 就用它）。这是中文场景的决定性优势。
4. **视口虚拟化**：只渲染可见行，10 万字文档不掉帧。
5. **Obsidian Live Preview 已验证这条路走得通**——这是最强的可行性背书：Obsidian 用 CM6 实现了与参考实现同样的"无缝即时渲染"，且支持桌面+移动端。

**唯一劣势**：无缝渲染的实现难度是四者中较高的（评分 3），因为装饰层要自己写。但这部分是**可控的增量工作**（约 1200–1500 行 TS），远比修 IME bug 便宜。

### 4.4 选型的最终定论

> **内核 = CodeMirror 6 + 自研 Live-Decoration 层**
> **渲染 = KaTeX（公式）+ Mermaid（图表，懒加载）+ 自研 GFM 表格/任务列表装饰**
> **外壳 = 一套 Web 代码，多端包装**

## 5. 跨端外壳选型论证

约束：**一套核心代码 → Windows 桌面 + Android 手机/平板**。这是本工程最大的成本杠杆：核心只有一份，外壳可换。

### 5.1 本机工具链实测（决定了本次能交付到哪一步）

| 工具 | 状态 | 影响 |
|---|---|---|
| Node 22.22.2 + npm 10.9.7 | ✅ 可用 | 核心可构建 |
| npm registry 连通 | ✅ 可用 | 依赖可安装 |
| WebView2 Runtime 155 | ✅ 已安装 | WebView2 外壳可行 |
| JDK 25 (Temurin) | ✅ 可用 | Android 打包的 Java 侧具备 |
| **Rust / cargo** | ❌ **未安装** | **Tauri 双端全部不可行** |
| **MSVC / VS Build Tools** | ❌ **未安装** | **Tauri Windows 不可行** |
| **Android SDK / NDK** | ❌ **未设置 ANDROID_HOME** | **APK 本机不能产出** |

### 5.2 外壳方案四选一

| 方案 | Windows | Android | 包体 | 本机可行性 | 判定 |
|---|---|---|---|---|---|
| **Electron** | ✅ 成熟 | ❌ 官方不支持 | 120–180MB | ✅ 预编译二进制，无需编译器 | **Windows 主选** |
| **Tauri 2** | ✅ | ✅（v2 支持） | 5–15MB | ❌ 缺 Rust + MSVC + NDK | 备选（体积最优，写配置备用） |
| **Capacitor** | ❌（有 Electron 适配器，冗余） | ✅ 标准方案 | APK ~8MB | ⚠️ 需 Android SDK 才能出包 | **Android 打包路径** |
| **PWA** | ✅（可安装） | ✅（可安装到主屏、离线） | 0（网页） | ✅ **立即可用** | **Android 一等公民** |

### 5.3 决策

> **Windows**：Electron（立即可跑，已验证 Electron 二进制可下载且无需本地编译）
> **Android**：**双轨制** ——
> - **轨道 1（立即可用）**：PWA。加到主屏后全屏运行、离线可用、支持文件打开/保存。对"手机和平板上使用同等功能"这个目标，PWA 已经能满足 90% 场景，且零安装门槛。
> - **轨道 2（可分发 APK）**：Capacitor 工程已生成并配好，装好 Android SDK 后执行一条命令即得 `.apk`。

**为什么 PWA 能当一等公民？** 因为现代 Android Chrome 已支持：
- `showOpenFilePicker` / `showSaveFilePicker`（File System Access API，Android Chrome 89+ 支持）
- Service Worker 离线缓存（断网可用）
- `display: standalone` 全屏（无浏览器地址栏，观感等同原生）
- 触屏手势（本工程专门做了移动端适配：工具栏替代快捷键、软键盘 viewport 处理）

**唯一 PWA 做不到的**：访问任意本地目录树（沙盒限制）。所以文件树面板在 PWA 下降级为"最近文件 + 单文件打开"，而 Electron/Capacitor 版有完整目录树。——这个降级在 `docs/internal/02` 里已显式标注。

## 6. 风险清单与对策

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| R1 | 装饰层在中文 IME 输入时闪烁/丢字 | 中 | 致命 | 全部装饰计算读 `view.composing`，composing 期间**冻结装饰**（下轮再算）；CM6 原生保证光标正确 |
| R2 | 隐藏定界符后，退格/删除行为错乱 | 高 | 高 | 用 `EditorView.atomicRanges`，把被 replace 的区间标记为原子；退格跨过整个 span |
| R3 | 表格/公式的"活控件"焦点与 CM6 视图冲突 | 高 | 中 | 采用 `Decoration.widget` + `ignoreEvent` 白名单；点击后先把光标 move 到该块，再渲染源码态（参考实现同款行为） |

## 9. 结论

1. **目的达成路径**：黑盒测绘 → 规格 → 净室实现。合法、可控、可维护。
2. **技术内核**：CM6 装饰层是本场景唯一同时满足"无损 / 中文可靠 / 长文性能 / 双端复用"的选择。
3. **跨端策略**：核心一份，外壳三包（Electron / PWA / Capacitor），成本被压到最低。
4. **真正的工作量不在"能不能渲染"，而在"打磨对不对味"** —— 这也是为什么 `docs/internal/02` 的功能测绘要细到快捷键和间距数值。
