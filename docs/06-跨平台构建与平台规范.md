# 跨平台构建与平台规范（macOS / Linux）

> 配套：`03-架构与技术规格.md`（模块职责）、`04-验证方案.md`（怎么证明做对了）、
> `releases/v0.6.0/notes.md`（发布说明）。
> 本文回答四件事：**怎么构建**、**要守哪些平台规范**、**功能对齐到什么程度**、**怎么验证**。

---

## 0. 一句话结论

macOS 与 Linux 版**都能构建出来**，且与 Windows / Android 共用同一套核心（`core/dist` + `desktop/main.js`）；
但 **macOS 的最后一步（codesign / 公证）只能在 Mac 上做**，Linux 的 AppImage / deb 也只能在 Linux 上做。
本机是 Windows，没有 Mac、没有 Linux、没有 WSL/Docker，所以**构建侧**能做的只有"把包做对、把包内事实验掉"，定位是：

> 运行证据不在构建机上，而在用户设备上。v0.8.2 已在 **Apple Silicon Mac** 与 **Linux Mint（tar.gz）** 上实测：启动、菜单、编辑保存、图片显示与新图标都正常（`docs/04` §3.9 / H31）。这台 Windows 机器仍然产不出该项证据，下表"不能验的"说的是**构建机视角**。

| 平台 | 产出状态 | 能验的 | 不能验的 |
|---|---|---|---|
| macOS arm64 | ✅ 完整 .app（tar.gz） | 包结构 / Mach-O 架构 / Info.plist / 符号链接 / 图标 / 前端完整性 | 真机启动、Gatekeeper 行为、codesign 是否通过 |
| macOS x64 | ✅ 完整 .app（tar.gz） | 同上 | 同上 |
| Linux x64 | ✅ 完整目录树（tar.gz） | ELF 架构 / 权限位（含 setuid）/ .desktop / 图标 / 前端完整性 | 真机启动、缺库情况、Wayland 表现 |

**没验过的就是没验过**，本文与发布说明都按这个口径写，不拿"结构正确"冒充"跑得起来"。

## 1. 交付物与构建方式

### 1.1 产物清单（v0.6.0 实测）

| 文件 | 平台 | 格式 | 大小 | 包内顶层 | 入口 |
|---|---|---|---|---|---|
| `Lypora-0.6.0-macos-arm64.tar.gz` | macOS 11+ / Apple Silicon | tar.gz | 95.8 MiB | `Lypora-0.6.0-macos-arm64/` | `Lypora.app` |
| `Lypora-0.6.0-macos-x64.tar.gz` | macOS 11+ / Intel | tar.gz | 100.2 MiB | `Lypora-0.6.0-macos-x64/` | `Lypora.app` |
| `Lypora-0.6.0-linux-x64.tar.gz` | Linux x86_64 / glibc ≥ 2.31 | tar.gz | 102.4 MiB | `Lypora/` | `lypora.sh` |
| `Lypora-0.6.0-win-x64.zip` | Windows 10/11 x64 | zip | 111.0 MiB | `Lypora/` | `Lypora.exe` |
| `Lypora-0.6.0-android.apk` | Android 10+ | APK | 10.6 MiB | — | 桌面图标 |

macOS 包**套一层版本目录**（`Lypora-<ver>-macos-<arch>/`）：解压不会把 `Lypora.app` / `LICENSE` 甩进
用户当前目录，同时两个架构的解压结果不会互相覆盖。Linux 包沿用 Electron 自身惯例 `Lypora/`，
`install.sh` 用 `dirname $0` 定位、目录名不影响安装。

### 1.2 构建命令

```bash
# 0) 前置：前端产物（三端共用，只构建一次）
cd core && npm install && npx vite build      # → core/dist

# 1) 取 Electron 官方预编译包（与宿主平台无关，镜像可换 npmmirror）
#    darwin-arm64 / darwin-x64 / linux-x64 各一份 v33.4.11
#    校验：sha256 必须与官方 SHASUMS256.txt 一致（脚本会打印，见 §5）
mkdir -p .tmp-elec && cd .tmp-elec
for p in darwin-arm64 darwin-x64 linux-x64; do
  curl -LO https://cdn.npmmirror.com/binaries/electron/33.4.11/electron-v33.4.11-$p.zip
done

# 2) macOS（两个架构各一条命令）
cd ../..
python tools/pack-mac.py --zip .tmp-elec/electron-v33.4.11-darwin-arm64.zip --arch arm64
python tools/pack-mac.py --zip .tmp-elec/electron-v33.4.11-darwin-x64.zip   --arch x64

# 3) Linux
python tools/pack-linux.py --zip .tmp-elec/electron-v33.4.11-linux-x64.zip

# 4) Windows（不变）
node tools/pack-win.mjs --zip

# 5) 结构校验（三端一起）
python tools/check-package.py
```

**依赖**：Node ≥20、Python 3.10+（用带 Pillow 的解释器，图标要缩放）。
Windows 上 `python` 默认解释器没装 Pillow，本项目用托管 venv：

```bash
P=~/.workbuddy/binaries/python/envs/default/Scripts/python.exe
"$P" tools/pack-mac.py --zip … --arch arm64
```

### 1.3 为什么这三个平台能在 Windows 上构建

1. **Electron 的 darwin/linux 分发包是官方预编译的 zip**，与宿主平台无关——只是解包重组；
2. **前端是纯静态文件**，主进程是纯 JS，不需要交叉编译；
3. 需要"编译"的东西（Mach-O、ELF）全都在官方包里现成躺着。

唯一踩不住的是**符号链接**：Windows 普通账户建不了 symlink（`ln -s` 直接 `Operation not permitted`，
已验证）。所以 `pack-mac.py` **不解压到磁盘**，而是把 zip 条目直接流式写进 tar，
遇到 symlink 条目就写 tar 的 `SYMTYPE` 条目。详见 §2.2。

## 2. macOS 平台规范

### 2.1 `.app` bundle 结构（本包实际形态）

```
Lypora.app/
├── Contents/
│   ├── Info.plist                          ← 我们重写（见 2.3）
│   ├── PkgInfo                             ← APPL????
│   ├── MacOS/
│   │   └── Lypora                          ← 由 Electron 改名，Mach-O，0755
│   ├── Frameworks/
│   │   ├── Electron Framework.framework/    ← 名字**不能改**（@rpath 里写死）
│   │   │   └── Versions/A/{Electron Framework, Libraries/, Resources/}
│   │   │       ↑ Versions/Current → A（符号链接）
│   │   ├── Lypora Helper.app/              ← 由 Electron Helper 改名
│   │   ├── Lypora Helper (GPU).app/
│   │   ├── Lypora Helper (Renderer).app/
│   │   ├── Lypora Helper (Plugin).app/
│   │   ├── Mantle.framework / ReactiveObjC.framework / Squirrel.framework
│   └── Resources/
│       ├── Lypora.icns                     ← 我们生成
│       ├── *.pak / icudtl.dat / locales/
│       ├── v8_context_snapshot.bin
│       └── app/                            ← 我们的应用
│           ├── main.js / preload.js / selftest-probe.js
│           ├── package.json                ← version 0.6.0，main: main.js
│           └── web/                        ← 就是 core/dist
```

顶层（`Lypora-0.6.0-macos-<arch>/`）除 `Lypora.app` 外还有：
`mac-finalize.command`（0755）、`README-macOS.txt`、`build-info.txt`、
`LICENSE` / `LICENSES.chromium.html` / `version`（Electron 分发包自带的三个文件，按原样保留，不重复写）。

**关键约束与理由**

| 约束 | 为什么 |
|---|---|
| `Contents/Frameworks/Electron Framework.framework` 名字不能动 | dyld 通过 `@rpath/Electron Framework.framework/…` 加载，改名立刻起不来 |
| `Versions/Current`、`Electron Framework`、`Resources`、`Libraries`、`Helpers` 必须是**符号链接** | macOS framework 的标准布局，dyld 与 codesign 都依赖；用目录顶替会出问题 |
| helper 必须跟着主程序改名（`Lypora Helper*.app`） | Chromium 由**主包名**推出 helper 路径；主程序叫 Lypora 而 helper 还叫 Electron，子进程就起不来。electron-builder 也是这么干的 |
| 去掉 `Resources/default_app.asar` | 否则 Electron 的默认应用会和 `resources/app` 抢入口 |
| 不打包 asar | `resources/app/` 目录形态同样被支持，改完 JS 不用重新打包，调试成本低 |

### 2.2 为什么是 tar.gz 而不是 dmg / zip

| 方案 | 可行性 | 结论 |
|---|---|---|
| `.dmg` | 需要 `hdiutil`，只有 macOS 有 | ❌ 做不了 |
| `.zip` | 需要写入 symlink 条目；Windows 上既建不了链接，Node 也没有内置 zip writer | ⚠️ 能写但风险高，无 macOS 可验证，不冒险 |
| **`.tar.gz`** | `tar` 原生支持 symlink 条目，可绕过文件系统直接构造 | ✅ 采用 |

代价：用户要 `tar xzf` 或双击解压，不是双击挂载。macOS 自带的"归档实用工具"能直接解 `.tar.gz`。

> 实测数字：arm64 / x64 两个包各含 **14 个符号链接**，一个不少（`check-package.py` 断言 ≥14，
> 且校验 `Versions/Current → A`）。

### 2.3 Info.plist（逐键说明）

| 键 | 值 | 规范/理由 |
|---|---|---|
| `CFBundleExecutable` | `Lypora` | 必须与 `Contents/MacOS/` 里的文件名一致 |
| `CFBundleIdentifier` | `app.lypora.editor` | 反向域名、全局唯一；与 Android `applicationId` 同名，便于识别 |
| `CFBundleName` | `Lypora` | ≤15 字符（菜单栏宽度限制） |
| `CFBundleDisplayName` | `Lypora` | Finder 显示名 |
| `CFBundleIconFile` | `Lypora.icns` | 不含扩展名也可，但写全更保险 |
| `CFBundlePackageType` | `APPL` | 应用包 |
| `CFBundleShortVersionString` | `0.6.0` | 用户可见版本 |
| `CFBundleVersion` | `0.6.0` | 构建号，单调递增 |
| `LSMinimumSystemVersion` | `11.0` | Electron 33 的下限（Chromium 129 起不再支持 10.15） |
| `NSHighResolutionCapable` | `true` | 缺了 Retina 下会糊成 1x |
| `NSPrincipalClass` | `AtomApplication` | Electron 的自定义 NSApplication 子类，别改 |
| `CFBundleDocumentTypes` | md / markdown / mdown / mkd / txt，`LSHandlerRank=Alternate` | 声明能打开哪些文件；`Alternate` = **不抢**系统默认，用户主动选才用 |

**刻意不写的**：`NSAppTransportSecurity`（本应用只加载 `file://`，没有任何网络请求，
不给自己放开 ATS 的口子）、`ElectronAsarIntegrity`（没用 asar）。

### 2.4 代码签名与 Gatekeeper（这是 macOS 最大的坑）

macOS 的签名是**分层**的，本包所处的层级必须说清楚：

| 层级 | 谁做 | 本包状态 |
|---|---|---|
| **单个 Mach-O 的内嵌签名** | Electron 官方 | arm64 包**有**（ad-hoc）；x64 包**完全没有**（实测：`cputype 01000007`、无 `LC_CODE_SIGNATURE`） |
| **bundle 封条**（`_CodeSignature/CodeResources`） | `codesign` | Electron 官方包**就没有**（zip 里 0 个 `_CodeSignature` 条目） |
| **ad-hoc 重签整个 bundle** | 用户 / `mac-finalize.command` | ✅ 由脚本在 Mac 上完成 |
| **Developer ID 签名 + 公证** | Apple 开发者账号 + `notarytool` | ❌ 没有证书，做不了 |

**为什么必须重签**
- Apple Silicon 内核要求可执行文件**至少有一个有效签名**，否则直接 `SIGKILL`（用户看到"闪一下就没了"）。
- x64 官方包连内嵌签名都没有，所以 x64 更需要这一步。
- 我们改过 `Info.plist`、加了 `Resources/app`——虽然不影响已内嵌的 Mach-O 签名（签名覆盖的是二进制本身），
  但既然要重签，就统一把整个 bundle 封一遍，让 `codesign --verify` 能过。

**为什么会有 quarantine**
从浏览器/聊天工具下载的文件会被打上 `com.apple.quarantine` 扩展属性，Gatekeeper 见"已隔离 + 未识别开发者"
就拦。`mac-finalize.command` 第一件事就是 `xattr -dr com.apple.quarantine`。

**没有 `_CodeSignature` 反而少一个坑**：如果包里有**失效**的封条，macOS 报的是
"应用已损坏，请移到废纸篓"——这个提示**无法通过右键打开绕过**，比"未识别开发者"难处理得多。
本包没有封条，所以走的是后者：右键 → 打开 → 确认即可。

`mac-finalize.command` 的实际内容（放在 tar 顶层目录里，用户 `sh mac-finalize.command`）：

```bash
xattr -dr com.apple.quarantine "Lypora.app"
codesign --force --deep --sign - "Lypora.app"
codesign --verify --deep --strict --verbose=2 "Lypora.app"
```

### 2.5 `.icns` 图标规范

`.icns` 是容器：`'icns'` + 4 字节总长 + 若干 `(4 字节类型, 4 字节长度, PNG)`。
**每个类型对应固定像素尺寸**，写错 Finder 会静默不显示。本包写入 11 档：

| 类型 | 尺寸 | 类型 | 尺寸 |
|---|---|---|---|
| `icp4` | 16 | `ic10` | 1024 |
| `icp5` | 32 | `ic11` | 32（16@2x） |
| `icp6` | 64 | `ic12` | 64（32@2x） |
| `ic07` | 128 | `ic13` | 256（128@2x） |
| `ic08` | 256 | `ic14` | 512（256@2x） |
| `ic09` | 512 | | |

源图是 `core/public/icons/icon-512.png`，用 Pillow `LANCZOS` 逐档缩放（1024 档是上采样，
512 源图放到 1024 会有轻微软化，`.icns` 允许只提供部分档位，先保证各档齐全）。

## 3. Linux 平台规范

### 3.1 目录结构与 FHS 对照

包内是**自包含目录**，不写系统目录：

```
Lypora/
├── lypora                 ← 主程序（ELF 64-bit LSB, x86-64, PIE）
├── lypora.sh              ← 启动包装（沙箱降级逻辑，见 3.3）
├── chrome-sandbox         ← SUID 沙箱助手，tar 里记录 4755
├── chrome_crashpad_handler
├── libEGL.so / libGLESv2.so / libffmpeg.so / libvk_swiftshader.so / libvulkan.so.1
├── icudtl.dat / v8_context_snapshot.bin / snapshot_blob.bin
├── *.pak                  ← chrome_100/200_percent.pak
├── locales/*.pak          ← 55 个语言包（Chromium 的，不是我们的 i18n）
├── resources/app/         ← 我们的应用（与 Windows 同一份）
├── lypora.desktop         ← 桌面入口模板
├── icons/hicolor/<n>x<n>/apps/lypora.png   ← 16/24/32/48/64/128/256/512
├── lypora.png             ← 512 根图标（AppImage 会用到）
├── install.sh / uninstall.sh
├── README-Linux.txt / build-info.txt
└── LICENSE / LICENSES.chromium.html
```

安装后的位置（`install.sh` 做的事，全部在 `$HOME` 下，**不需要 root**）：

| 内容 | 目标路径 | 对应 FHS / XDG |
|---|---|---|
| 程序本体 | `$XDG_DATA_HOME/lypora`（默认 `~/.local/share/lypora`） | XDG data |
| 桌面入口 | `~/.local/share/applications/lypora.desktop` | XDG applications |
| 图标 | `~/.local/share/icons/hicolor/<n>x<n>/apps/lypora.png` | hicolor 主题规范 |
| 命令行入口 | `~/.local/bin/lypora`（符号链接式 shim） | XDG bin |

### 3.2 `.desktop` 规范

```ini
[Desktop Entry]
Type=Application
Name=Lypora
GenericName=Markdown Editor
Comment=…
Exec=lypora.sh %F          # 安装时被 sed 成本机的绝对路径
Icon=lypora                # 与 icons/hicolor/*/apps/lypora.png 对应
Terminal=false
Categories=Office;TextEditor;Utility;
MimeType=text/markdown;text/x-markdown;text/plain;
Keywords=markdown;editor;md;txt;
StartupNotify=true
StartupWMClass=lypora     # 少了它任务栏会出现两个图标
```

| 键 | 为什么必须 | 后果 |
|---|---|---|
| `Exec` | 必须可执行、可用绝对路径 | 缺了菜单项点了没反应 |
| `Icon` | 与 hicolor 目录里的文件名（不含 .png）一致 | 缺了显示齿轮占位图 |
| `MimeType` | 桌面环境据此建立"用什么打开 .md"的关联 | 缺了文件管理器里选不到本应用 |
| `Categories` | 应用菜单归类 | 缺了只能搜到、不在分类里 |
| `StartupWMClass` | 让窗口与桌面项建立归属 | 缺了任务栏分组错乱/图标分身 |
| `%F` | 支持"用本应用打开多个文件" | 缺了拖文件到图标无反应 |

### 3.3 `chrome-sandbox` 与 SUID（Electron 通病）

Electron 的渲染进程默认走 SUID 沙箱，要求：

```
chrome-sandbox  owner=root:root  mode=4755
```

tar 能记录 `4755`（本包已写进 tar 头，`check-package.py` 断言 `S_ISUID`），但**解压时是否生效取决于解压器与用户权限**。
不满足时 Electron 直接报：

```
The SUID sandbox helper binary was found, but is not configured correctly
```

然后退出——用户看到的就是"点了没反应"。三层兜底：

1. `install.sh` 里 `sudo chown root:root + chmod 4755`（有 sudo 就走这条，沙箱保留）；
2. `lypora.sh` 启动前检测 `[ -u "$sb" ] && stat -c %u == 0`，不合格就自动 `--no-sandbox` 并打印提示；
3. README 里给出裸命令，供不想用脚本的人手动修。

`--no-sandbox` 会关闭渲染进程的 OS 级隔离，**只在沙箱确实配不好时降级**，不是默认路径。

### 3.4 兼容性要求

| 项 | 要求 | 依据 |
|---|---|---|
| 架构 | x86_64（amd64） | 只出了 linux-x64；arm64 需要另取 `electron-v33.4.11-linux-arm64.zip`（脚本已通用，加个参数即可） |
| glibc | ≥ **2.31**（Ubuntu 20.04 / Debian 11 / Fedora 32 / RHEL 9+） | Electron 33 的构建基线 |
| 显示 | X11 或 Wayland（Wayland 走 XWayland） | Chromium 默认路径 |
| 桌面库 | GTK3、libnss3、libasound2、libgbm1、libxss1 | Chromium 常规依赖 |
| 内核 | 支持 unprivileged user namespace，或 sandbox 配好 SUID | 二选一 |

### 3.5 为什么没有 AppImage / deb / rpm

| 方案 | 阻塞点 | 替代 |
|---|---|---|
| AppImage | `appimagetool` 是 ELF，Windows 跑不了（本机无 WSL、无 Docker——WSL 被安全策略禁用、`docker` 不存在） | 在 Linux 上一条命令自己做，README 里给了完整步骤 |
| `.deb` | `dpkg-deb` 同上 | `install.sh` 完成同等效果（装到 `~/.local`，不需要 root） |
| `.rpm` | `rpmbuild` 同上 | 同上 |
| Snap / Flatpak | 需要各自的服务端与签名体系 | 超出本项目范围 |

**这是有意如实标注的缺口，不是遗漏。**

| 字数统计 / 大纲 / 字号缩放（Ctrl 或 ⌘ + 滚轮） | ✅ | ✅ | |
| 关窗守卫（脏文档三按钮） | ✅ | ✅ | 同一套 `closeGuard` |
| 单实例 + 命令行传文件 | ✅（见 4.2） | ✅ | |
| `--selftest` 自检 | ✅ 可用 | ✅ 可用 | 命令：`Lypora.app/Contents/MacOS/Lypora --selftest` |

**证明"同一份前端"的方式**：`check-package.py` 对 tar 里的 `resources/app/web/assets/index-*.js`
与 `core/dist/assets/` 做 sha256 比对，两个 macOS 包与 Linux 包都通过。

### 4.2 平台差异（必须差异，不是缺陷）

| 项 | Windows | macOS | Linux | 原因 |
|---|---|---|---|---|
| 快捷键显示 | `Ctrl+S` | `⌘S` / `⇧⌘Z` | `Ctrl+S` | 平台惯例；`ui/keys.ts` 统一格式化，功能层一直是 `ctrlKey \|\| metaKey`，CM6 用 `Mod-` |
| 应用菜单 | 无（自绘） | 系统菜单栏只有「关于/隐藏/退出 + 窗口」 | 无（自绘） | mac 上没应用菜单就没有 ⌘Q；**刻意不给"编辑"菜单**——菜单加速键会抢走 ⌘Z，破坏 CM6 的撤销粒度 |
| 关窗后行为 | 退出应用 | 应用存活，点 Dock 图标重开窗口 | 退出应用 | macOS 惯例（`window-all-closed` 不 quit + `activate` 重建） |
| 双击 `.md` 打开 | argv 传路径 / 文件关联 | **`open-file` 事件** | argv 传路径 | macOS 不通过命令行传文件；`open-file` 可能早于窗口创建，故做了待开队列 |
| 图标格式 | `.ico`（rcedit 写进 exe） | `.icns`（Info.plist 引用） | PNG（hicolor 多档） | 各自的规范 |
| 首个文件投递时机 | 窗口加载后 400ms | 同左（队列在 `open-file` 累积） | 同左 | 三端统一走 `pendingOpen` 队列 |
| 沙箱 | 无 SUID 概念 | 系统级（无需配置） | 需 `chrome-sandbox` SUID 或降级 | §3.3 |

**一个 macOS 上才暴露的真实 bug（已修）**：`allowClose` 是模块级变量，原来的写法一旦关过一次窗就永远为 `true`；
Windows 上关窗即退出、看不出来，macOS 关窗不退出、窗口重建后再关窗会**跳过脏数据确认直接关**。
现在 `createWindow()` 里复位 `allowClose/winReady`。

### 4.3 不支持 / 未实现（与 Windows 一致）

- 自动更新（全平台都没有）
- 拼写检查、图床、云同步、协作
- 表格单元格内联编辑（点表格转源码编辑）

### 4.4 平台专属缺口

| 平台 | 缺口 | 影响 |
|---|---|---|
| macOS | 无公证；无 `.dmg`；无 Apple Silicon + Intel 通用二进制（`lipo` 不可用，只出两个独立包） | 首次打开需右键放行一次；用户要按架构选包 |
| macOS | 不抢系统默认打开方式（`LSHandlerRank=Alternate`） | 需手动"始终以此方式打开" |
| Linux | 无 AppImage / deb / rpm | 只能用 tar.gz + install.sh |
| Linux | 无系统托盘、无全局菜单 | 与 Windows 行为一致，非缺陷 |
| 两者 | 未做真机启动测试 | 见 §5.2 |

### 5.1 已执行的验证（可复现）

```bash
python tools/check-package.py      # 三个包一起验，退出码 0/1/2
```

`v0.6.0` 实测输出：

```
[check] ✓ Lypora-0.6.0-linux-x64.tar.gz  102.4 MiB  条目 187  链接 0
[check] ✓ Lypora-0.6.0-macos-arm64.tar.gz  95.8 MiB  条目 336  链接 14
[check] ✓ Lypora-0.6.0-macos-x64.tar.gz  100.2 MiB  条目 336  链接 14
         i x64 主可执行未签名（与 Electron 官方包一致），需 mac-finalize 做 ad-hoc 签名

```

断言清单（每条都是一个具体的失败模式）：

| # | 断言 | 失败意味着 |
|---|---|---|
| 1 | 顶层目录名 == `Lypora-<版本>-macos-<架构>/`；`Info.plist` 可解析且 9 个关键键值正确 | 解压污染当前目录，或 Finder 显示成 Electron / 图标错 / 版本错 |
| 2 | `CFBundleDocumentTypes` 含 `md` | 双击 .md 不认 |
| 3 | 无 `NSAppTransportSecurity` | 给自己开了不必要的网络口子 |
| 4 | 主可执行 Mach-O 架构 == 目标架构（arm64=0x0100000c / x64=0x01000007） | 装错包，`bad CPU type` |
| 5 | 主可执行有 x 位 | 双击无反应 |
| 6 | arm64 主可执行有 `LC_CODE_SIGNATURE`；x64 若没有则记为 note | Apple Silicon 直接 SIGKILL |
| 7 | `Electron Framework.framework/Versions/A/…` 存在 | dyld 找不到主框架 |
| 8 | 4 个 `Lypora Helper*.app` 及其可执行文件存在 | 渲染/GPU/插件进程起不来（白屏） |
| 9 | 符号链接 ≥14 个，且 `Versions/Current → A` | Windows 打包的典型事故：链接变普通文件 |
| 10 | `resources/app/{main.js,preload.js,package.json,web/index.html}` 齐全 | 启动即报 `Cannot find module` |
| 11 | `app/package.json` 的 `version` == 发布版本，`main == main.js` | 关于框/版本信息与实际不符 |
| 12 | `Lypora.icns` 魔数为 `icns` 且 >10KB | 图标空白 |
| 13 | 无 `_CodeSignature`、无 `default_app.asar`、无 `Electron Helper` 残留 | 前者被判 damaged，中者抢入口，后者子进程起不来 |
| 14 | Linux 主程序 `ELF64 / LSB / EM_X86_64 / ET_DYN` | 架构不符或不可执行 |
| 15 | `chrome-sandbox` 是 ELF 且 tar 头带 `S_ISUID` | 沙箱起不来，只能 `--no-sandbox` |
| 16 | `locales/*.pak` ≥20 | Chromium 语言包缺失 |
| 17 | `.desktop` 含 `Type/Name/Exec/Icon/Categories/MimeType(text/markdown)/StartupWMClass` | 菜单项无效、关联失效、任务栏分身 |
| 18 | 8 档图标均为 PNG 且像素尺寸与目录名一致 | 图标模糊或拉伸 |
| 19 | `lypora.sh` / `install.sh` / `uninstall.sh` 有 x 位 | 脚本跑不了 |
| 20 | 包内无 `.exe` / `.dll` | 打错平台 |

**Electron 分发包的来源校验**：三个 zip 的 sha256 与官方 `SHASUMS256.txt` 逐字节一致
（`9c763751…` arm64 / `67f3b851…` x64 / `212d431c…` linux）——不是"从某处下的就信了"。

**前端一致性校验**：tar 内 `web/assets/index-*.js` 与 `core/dist/assets/` 同名文件 sha256 相同
（macOS arm64/x64 与 Linux 三个包都验过）。

## 6. 已知限制汇总

1. **macOS 未公证**：没有 Apple 开发者账号。ad-hoc 签名不等于公证，首次启动必须人工放行一次。
2. **没有 `.dmg`**：`hdiutil` 只有 macOS 有。用户拿到的是 `.tar.gz`。
3. **两个架构分开发**：`lipo` 不可用（那是 macOS 工具），不做 universal binary。Apple Silicon 用户请装 `arm64`。
4. **Linux 只有 x64**：arm64 需另取 `electron-v33.4.11-linux-arm64.zip`，脚本本身通用。
5. **Linux 无 AppImage/deb/rpm**：`appimagetool`/`dpkg-deb` 在 Windows 上跑不了。
6. **真机证据已补上，但只覆盖两个点**：v0.8.2 在 Apple Silicon Mac 与 Linux Mint（tar.gz）上跑通（§5.2 已更新）。仍未覆盖：Intel `macos-x64` 包、deb / rpm / AppImage 装完后的运行、Wayland、缺库场景。构建机自身仍产不出运行证据（§5.1 是结构证据）。
7. **`--no-sandbox` 降级路径**：Linux 上沙箱没配好时会自动降级，安全性略降，README 已写明。
