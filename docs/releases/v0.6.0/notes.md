## 本版新增

### 1. macOS 版

不是「把 Linux 包改个名」。产物是一个真正的 `.app` bundle：

```
Lypora-0.6.0-macos-arm64/
├── Lypora.app/Contents/
│   ├── Info.plist              ← 重写：bundle id / 文档类型 / 最低系统 / Retina
│   ├── MacOS/Lypora            ← 主程序，helper 跟着改名（Lypora Helper*.app）
│   ├── Frameworks/             ← Electron Framework，含 14 个符号链接
│   └── Resources/
│       ├── Lypora.icns         ← 手写 icns 容器，11 档尺寸
│       └── app/                ← 与 Windows 版一字不差的前端 + 主进程
├── mac-finalize.command        ← 去 quarantine + ad-hoc 重签 + 校验
├── README-macOS.txt
└── LICENSE / LICENSES.chromium.html / version
```

**签名只有 ad-hoc 一层。** 没有 Apple Developer ID 证书，也就没有公证（notarytool 需要付费账号）。
所以首次打开会被 Gatekeeper 拦住：右键「打开」→ 再点「打开」，或者先跑 `mac-finalize.command`。
包内**不含** `_CodeSignature` 目录——一个内容对不上的签名封条比没有封条更糟：有封条但校验失败，
macOS 会报「应用已损坏，应移到废纸篓」，这个提示用户绕不过去；没有封条只会报「未识别开发者」，可以绕过。

**文件关联是「备选」级别**（`LSHandlerRank = Alternate`）：装完不会抢走你现有的 `.md` 默认打开方式，
需要手动在「打开方式」里选一次。我不想在别人的机器上偷偷改默认程序。

**菜单栏按 macOS 惯例给了 App 菜单和窗口菜单，但刻意没给 Edit 菜单。** 给了 `role: 'editMenu'` 之后，
⌘Z / ⌘C / ⌘V 会被系统菜单先截走，CodeMirror 的 `history()` 收不到事件——撤销会失效。同理，
`Ctrl+Y` 这类 Windows 习惯的键在 macOS 上映射成 `⌘⇧Z`（`core/src/ui/keys.ts`），只影响**显示**，
功能层一直是 `ctrlKey || metaKey`，两边都能用。

**从 Finder 拖/双击打开 `.md` 走 `open-file` 事件**，而 macOS 可能在窗口创建之前就把它发过来。
主进程改成一个待开队列 + 窗口就绪门闩（`pendingOpen` / `winReady`），不会丢文件。

### 2. Linux 版

```
Lypora/
├── lypora                      ← 主程序（ELF 64-bit，x86-64）
├── lypora.sh                   ← 启动器：检查 sandbox SUID，不合格则 --no-sandbox
├── install.sh / uninstall.sh   ← 安装 / 卸载
├── lypora.desktop              ← Exec / Icon / MimeType / Categories / StartupWMClass
├── chrome-sandbox              ← 权限位 root:root 4755
├── resources/app/              ← 同一份前端 + 主进程
└── icons/hicolor/{16,24,32,48,64,128,256,512}x…/apps/lypora.png
```

**`chrome-sandbox` 是个真问题。** Chromium 的 setuid 沙箱要求这个文件属于 `root` 且带 SUID 位；
普通用户解压出来是 `自己:自己 0755`，直接启动会得到
`The SUID sandbox helper binary was found, but is not configured correctly`，然后进程退出。三层兜底：

1. `install.sh` 用 `sudo` 设成 `root:root 4755`（推荐路径）；
2. 没有 sudo 时 `lypora.sh` 自己检测——`[ -u file ]` 且属主是 0 才 `exec` 主程序，否则加 `--no-sandbox`
   并打一行警告。功能全部可用，只是少了进程隔离；
3. 两条路都不走（直接 `./lypora`）时，README 里写了手改命令。

**`.desktop` 的 `StartupWMClass=lypora` 不能省。** 少了它，任务栏/程序坞会把窗口认成另一个应用，
图标分身成两个。

**安装是 per-user 的**：`$XDG_DATA_HOME/lypora`（默认 `~/.local/share/lypora`）+ `~/.local/share/applications`
里的桌面项 + `~/.local/bin/lypora` 软链。不写 `/usr`、不动 `/etc`，卸载就是 `./install.sh --uninstall`。

### 3. 跨平台验证工具

新增 `tools/check-package.py`：不需要 macOS / Linux，直接读 tar.gz 做 20 项断言——Mach-O 架构与
`LC_CODE_SIGNATURE`、ELF 类型与机器码、`Info.plist` 九个键、`.desktop` 七个键、8 档图标尺寸、
14 个符号链接的指向、`chrome-sandbox` 的 SUID 位、包内前端与 `core/dist` 是否逐文件一致。

它证明的是「包是对的」，**不是「能起来」**。这台构建机是 Windows，没有 Mac、没有 Linux 发行版，
WSL 与 Docker 都不可用——所以 macOS / Linux 包**没有在任何真机上启动过**。这一条写在 README、
`docs/04` 和 `docs/06` 三处，别让它被当成「已测试」。

### 4. 顺带修掉一个只在 macOS 上暴露的 bug

`allowClose` 是主进程里的模块级变量，关窗时置 true。Windows / Linux 上关窗就是退出进程，所以从来没人
发现它没被复位；macOS 上关窗不退出应用，点 Dock 图标会重建窗口——新窗口沿用 `allowClose = true`，
`close` 事件里那段「脏数据确认」被整段跳过，**关窗守卫悄悄失效**。现在 `createWindow()` 开头统一复位
`allowClose` 与 `winReady`。

顺带把「首次启动带文件参数」和「第二实例转发文件」两条路径收敛到同一条队列（`queueOpenPath`），
三端行为一致，不再有两份重复的读文件逻辑。

### 5. Windows / Android 的同步改动

除版本号（`versionCode 7`）外，两个平台继承上述主进程修复。前端与 macOS / Linux 包完全同源，
所以三个平台上「渲染、编辑、字号、表格列宽、菜单、i18n、导出」的行为是一份代码。

## 安装方式

### Windows 10/11 x64

1. 解压 `Lypora-0.6.0-win-x64.zip`，得到 `Lypora\` 文件夹（**保持文件夹结构完整**，不要只拷 exe）。
2. 双击 `Lypora\Lypora.exe`。
3. 首次运行若出现 SmartScreen 提示：点「更多信息」→「仍要运行」。exe **未做代码签名**，这是原因。
4. 想用「打开方式」关联 `.md`：右键任意 `.md` → 打开方式 → 选择其他应用 → 浏览到 `Lypora.exe` → 勾选「始终使用此应用」。
5. 卸载 = 删除该文件夹；配置在 `%APPDATA%\lypora-desktop`，可一并删除。

### macOS 11 及以上

1. 先看架构：Apple 芯片（M1 及以后）下 `arm64` 包，Intel 下 `x64` 包。不确定就在终端跑 `uname -m`。
2. `tar xzf Lypora-0.6.0-macos-arm64.tar.gz`，得到 `Lypora-0.6.0-macos-arm64/`。
3. 二选一：
   - `sh mac-finalize.command`（推荐：清掉 quarantine 属性并做一次 ad-hoc 重签，最后 `codesign --verify`），然后 `open Lypora.app`；
   - 或者把 `Lypora.app` 拖进「应用程序」，右键 →「打开」→ 再点一次「打开」。
4. 之后从「启动台」或「应用程序」启动即可，系统会记住这次放行。
5. 卸载 = 删掉 `Lypora.app`；配置在 `~/Library/Application Support/lypora-desktop`。

### Linux x86-64

```bash
tar xzf Lypora-0.6.0-linux-x64.tar.gz
cd Lypora
./install.sh        # 装到 ~/.local/share/lypora + 菜单项 + ~/.local/bin/lypora
lypora              # 之后任意位置都能起
```

只想试一下就 `cd Lypora && ./lypora.sh`。卸载：`./install.sh --uninstall`。
配置在 `~/.config/lypora-desktop`。

**没有 `.deb` / `.rpm` / AppImage / Flatpak。** deb/rpm 要 `dpkg-deb` / `rpmbuild`，AppImage 要
`appimagetool`，这三个在 Windows 上都跑不了；Flatpak 需要一份 manifest 和运行时，属于另一个项目的工作量。
tar.gz + `install.sh` 是这台构建机能诚实交付的形式。

### Android 10 及以上

1. 把 `Lypora-0.6.0-android.apk` 传到手机（数据线 / 微信文件传输助手 / 网盘均可）。
2. 点开安装。系统会提示「未知来源应用」——这是侧载 APK 的正常提示，在弹窗里允许该来源即可。
   （或用电脑：`adb install -r Lypora-0.6.0-android.apk`）
3. 首次启动约 1–2 秒加载 WebView 内核，随后进入编辑器。
4. 卸载会**一并删除**应用内的文档，卸载前先把要留的文件用分享面板导出去。

## New in this release

### 1. macOS

Not "rename the Linux build". The artefact is a real `.app` bundle: rewritten `Info.plist` (bundle id,
document types, minimum OS, Retina), helpers renamed along with the main executable (`Lypora Helper*.app`),
a hand-built `.icns`, and the same `Resources/app` payload the Windows build ships — 14 symlinks inside
Electron Framework intact.

**Signing stops at ad-hoc.** No Apple Developer ID, therefore no notarisation (notarytool needs a paid
account). Gatekeeper stops the first launch: right-click → **Open** → **Open**, or run
`mac-finalize.command` first. The bundle deliberately carries **no** `_CodeSignature` directory — a seal whose
contents no longer match is worse than no seal at all: macOS reports *"the app is damaged and should be moved
to the Trash"*, which a user cannot bypass, whereas a missing seal only yields *"unidentified developer"*,
which they can.

**File association is `LSHandlerRank = Alternate`:** installing does not steal your existing `.md` handler.
Pick Lypora once in *Open With* if you want it. I'm not quietly changing anyone's defaults.

**The menu bar gets the App and Window menus, deliberately not an Edit menu.** With `role: 'editMenu'`, macOS
intercepts ⌘Z / ⌘C / ⌘V before the page sees them and CodeMirror's `history()` stops working. Likewise,
Windows-style `Ctrl+Y` displays as `⌘⇧Z` on macOS (`core/src/ui/keys.ts`) — display only; the handlers have
always accepted `ctrlKey || metaKey`.

**Opening a `.md` from Finder arrives as an `open-file` event that may fire before the window exists.** The
main process now queues paths (`pendingOpen` / `winReady`) instead of dropping them.

### 2. Linux

`Lypora/` contains the executable, `lypora.sh` (launcher), `install.sh` / `uninstall.sh`, `lypora.desktop`,
8 sizes of hicolor icons, and a `chrome-sandbox` marked `root:root 4755`.

**`chrome-sandbox` is a real problem.** Chromium's setuid sandbox requires that file to be owned by root with
the SUID bit; an ordinary user extracting the tarball gets `self:self 0755`, and the app dies with
*"The SUID sandbox helper binary was found, but is not configured correctly"*. Three layers of fallback:
`install.sh` sets it with `sudo`; if you decline, `lypora.sh` detects the condition (`[ -u ]` plus owner 0)
and falls back to `--no-sandbox` with a warning — everything works, minus process isolation; and the README
documents the manual `chown`/`chmod` for anyone who wants neither.

`StartupWMClass=lypora` in the `.desktop` file is not optional: without it the taskbar treats the window as a
different application and shows a duplicate icon.

**Installation is per-user** — `$XDG_DATA_HOME/lypora`, a desktop entry under `~/.local/share/applications`,
and a `~/.local/bin/lypora` shim. Nothing writes to `/usr` or `/etc`; `./install.sh --uninstall` removes it all.

### 3. A cross-platform verification tool

`tools/check-package.py` runs 20 assertions straight out of the tarballs, without a Mac or a Linux box:
Mach-O architecture and `LC_CODE_SIGNATURE`, ELF class/machine, nine `Info.plist` keys, seven `.desktop` keys,
8 icon sizes, the targets of 14 symlinks, the SUID bit on `chrome-sandbox`, and whether the bundled front end
matches `core/dist` file by file.

It proves the **package is correct**, not that it **starts**. This build machine runs Windows; there is no Mac,
no Linux distribution, and neither WSL nor Docker is available here — so the macOS and Linux builds have
**never been launched on real hardware**. That statement appears in the README, `docs/04` and `docs/06` on
purpose; please don't read the green checkmarks as something they are not.

### 4. One bug that only macOS could expose

`allowClose` is module-level state set to true when a window is closing. On Windows and Linux closing the
window quits the process, so nobody noticed it was never reset; on macOS the app stays alive and clicking the
Dock icon rebuilds the window — which inherited `allowClose = true`, skipped the unsaved-changes branch of the
`close` handler, and **silently dropped the guard**. `createWindow()` now resets `allowClose` and `winReady`
up front.

Along the way, "first launch with a file argument" and "second instance forwards a file" were folded into one
queue (`queueOpenPath`), so all three platforms behave the same and the duplicate read-file logic is gone.

### 5. Windows / Android

Beyond the version bump (`versionCode 7`), both inherit the main-process fixes. The front end is the same
source as the macOS / Linux packages, so rendering, editing, font sizing, table column widths, menus, i18n and
export behave identically on all three desktop platforms.

## Installation

### Windows 10/11 x64

1. Unzip `Lypora-0.6.0-win-x64.zip` into a `Lypora\` folder (**keep the folder intact** — don't copy just the exe).
2. Double-click `Lypora\Lypora.exe`.
3. If SmartScreen complains on first run: *More info* → *Run anyway*. The exe is **not code-signed**; that's why.
4. To associate `.md` files: right-click any `.md` → Open with → Choose another app → browse to `Lypora.exe` → *Always use this app*.
5. Uninstalling = delete the folder. Settings live in `%APPDATA%\lypora-desktop`; delete that too if you want a clean slate.

### macOS 11 and later

1. Check the architecture: `arm64` for Apple silicon, `x64` for Intel (`uname -m` if unsure).
2. `tar xzf Lypora-0.6.0-macos-arm64.tar.gz` → `Lypora-0.6.0-macos-arm64/`.
3. Either run `sh mac-finalize.command` (clears quarantine, ad-hoc re-signs, then `codesign --verify`) and
   `open Lypora.app`, or drag `Lypora.app` to *Applications* and right-click → **Open** → **Open** once.
4. Subsequent launches work normally; macOS remembers the exception.
5. Uninstalling = delete `Lypora.app`. Settings live in `~/Library/Application Support/lypora-desktop`.

### Linux x86-64

```bash
tar xzf Lypora-0.6.0-linux-x64.tar.gz
cd Lypora
./install.sh        # installs to ~/.local/share/lypora, adds a menu entry and ~/.local/bin/lypora
lypora
```

To try it without installing: `cd Lypora && ./lypora.sh`. Uninstall with `./install.sh --uninstall`.
Settings live in `~/.config/lypora-desktop`.

**No `.deb` / `.rpm` / AppImage / Flatpak.** Building those needs `dpkg-deb`, `rpmbuild`, `appimagetool` or a
Flatpak runtime — none of which run on Windows. tar.gz plus `install.sh` is what this build machine can
honestly produce.

### Android 10 and later

1. Copy `Lypora-0.6.0-android.apk` to the phone (USB, a file-transfer chat, or cloud storage — all fine).
2. Tap to install. Android will warn about unknown sources; that's normal for sideloaded APKs — allow that source in the dialog.
   (Or from a computer: `adb install -r Lypora-0.6.0-android.apk`)
3. First launch spends 1–2 seconds warming up the WebView, then you land in the editor.
4. Uninstalling **deletes the documents stored inside the app**. Export what you want to keep first.

**Intentional per-platform differences**

- macOS undo/redo is ⌘Z / ⌘⇧Z; there is no Ctrl+Y, and the menus say so.
- macOS does not claim the default `.md` handler (`Alternate`); Linux registers `MimeType` and lets the desktop
  environment decide precedence.
- Linux runs with `--no-sandbox` when the SUID helper isn't installed. The UI is identical.

## Notes and caveats

- No auto-update. Upgrading = download and overwrite (replace the Windows folder, swap the `.app`, re-run
  `install.sh`, install the same-signed APK over the old one).
- This is a **vibe coding** project: broad feature coverage, uneven code quality. Treat it as a draft, and open
  an issue when something breaks.
- Very large documents (>1 MB or tens of thousands of lines) may drop frames while scrolling. Exported HTML
  references images by relative path, so moving the HTML alone will break them.
- **The macOS and Linux packages have never been launched on real hardware.** Structure checks are green
  (`python tools/check-package.py`, 20 assertions), but the first double-click is the first run. If it doesn't
  start, please open an issue with `build-info.txt` and your OS version.
- macOS is not notarised, Windows is not code-signed, the APK is debug-signed — all three will warn once.
