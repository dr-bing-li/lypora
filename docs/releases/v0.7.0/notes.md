CI 自己打包、自己进容器真装一遍、自己把安装包和 `SHA256SUMS.txt` 传上 Release，你打开 Release 页就能下。

Linux now has package-manager-installable forms for the first time: `.deb`, `.rpm` and AppImage — four paths
including the existing tarball. Same bytes, same staged tree, different wrappers. This release also brings the
GitHub Actions pipeline: push a `v*` tag and CI builds the packages, actually installs them inside containers,
and uploads the installers plus `SHA256SUMS.txt` to the Release.

## 本版新增

### 1. deb

```
lypora_0.7.0_amd64.deb
├── DEBIAN/{control,postinst,prerm,postrm,md5sums}     ← control 由 packaging/debian/control.in 渲染
├── opt/lypora/                                        ← 主程序 + resources/app + locales
├── usr/bin/lypora                                     ← 3 行 shell，exec 到 lypora.sh
└── usr/share/{applications,icons,metainfo,licenses,doc}
```

`sudo apt install ./lypora_0.7.0_amd64.deb` 装完就能在应用菜单里搜到、在终端里 `lypora` 起来。
`postinst` 刷新 `update-desktop-database` 与 `gtk-update-icon-cache`，装完不用注销。

**依赖写成 `a | b` 是必须的。** Ubuntu 24.04 做 t64 迁移后 `libasound2` 改名 `libasound2t64`，
`libatk-bridge2.0-0` → `libatk-bridge2.0-0t64`，`libcups2` → `libcups2t64`。只写老名字的包在 22.04 上装得
上、在 24.04 上直接缺依赖装不上。三个都写成 `老名 | 新名`，两个 LTS 都满足。

### 2. rpm

`sudo dnf install ./lypora-0.7.0-1.x86_64.rpm`，落点与 deb 完全一致（这就是"一棵树"的好处：
`%install` 直接 `cp -a` 暂存树，没有再解释一遍布局）。

spec 里几个为了"别把时间浪费在无意义的事上"的开关：`%global __os_install_post %{nil}` 关掉 brp-strip、
`%global debug_package %{nil}` 关掉 debuginfo——Electron 的二进制本来就是 strip 过的，再跑一遍要多花
几分钟且产出 0 收益。

**`%install` 末尾那句 `chmod 4755 chrome-sandbox` 不能删。** GNU `cp -a` 以**非 root 身份**复制
"root 属主 + setuid"的文件时，保不住属主就不肯造 setuid 文件，会主动把 s 位去掉。rpmbuild 通常以普通用户
跑，所以 deb（在 chown 前封好）是对的、rpm 装出来是 `0755`，报
`The SUID sandbox helper binary was found, but is not configured correctly`。
这一条烧掉了四轮 CI，排查过程记在 `docs/04` V48。

### 3. AppImage

```bash
chmod +x Lypora-0.7.0-linux-x64.AppImage && ./Lypora-0.7.0-linux-x64.AppImage
```

不给 root 权限、不写任何系统目录、删掉文件就是卸载。代价是**沙箱必然降级**：AppImage 里没有 root，
`chrome-sandbox` 的 SUID 无从生效，所以 `AppRun` 直接带 `--no-sandbox` 启动。这是 Electron 打 AppImage
的固有代价，不是配置错误——界面和功能没有任何区别，少的只是渲染进程的 OS 级隔离。

### 4. GitHub Actions：推 tag 就发

`.github/workflows/linux-installers.yml`，触发条件是 `push: tags: ['v*']`（也可以手动指定已存在的 tag）：

```
检出 → 读版本号 → npm ci && npm run build → 下 Electron v33.4.11
     → linux-stage.py 摊 FHS 树 → tar.gz / deb / rpm / AppImage
     → 结构检查（dpkg-deb -I/-c、rpm -qip/-qplv、file）
     → debian:12 容器里真装一遍 → fedora:40 容器里真装一遍
     → 生成/合并 SHA256SUMS.txt → gh release upload --clobber
     → xvfb 下 --selftest（尽力而为，超时或失败都不阻断发布）
```

**"容器里真装一遍"是这套流程的核心价值。** 它不是解压看看文件在不在，而是 `apt install ./x.deb` /
`dnf install ./x.rpm` 真的走一遍包管理器，然后断言四件事：装上（`dpkg -s` / `rpm -q` 成功）、
文件落对（`/usr/bin/lypora` 可执行）、**setuid 位还在**（`test -u /opt/lypora/chrome-sandbox`）、
能执行。setuid 那一条正是上面那个 bug 的照妖镜——本地 `python tools/linux-stage.py` 一切正常，
只有真装一遍才看得见。

`SHA256SUMS.txt` 是**合并**而不是覆盖：CI 先 `gh release download` 拿线上已有的清单，剥掉自己这四个
文件名，再拼上新的重新排序。所以 Windows / macOS / APK 的条目不会因为 CI 重跑而消失。

### 5. 其它平台

Windows、macOS、Android 只跟着改版本号（`versionCode 8`），代码与 0.6.0 一致。
五个平台的 `resources/app` 是同一份 `core/dist`——同样的 `index.html` sha256 前 12 位
`c9beee20cc04`。

## 安装方式

### Debian / Ubuntu（deb）

```bash
sudo apt install ./lypora_0.7.0_amd64.deb     # 推荐，apt 会顺带解决依赖
# 或：sudo dpkg -i ./lypora_0.7.0_amd64.deb && sudo apt -f install
```

验证：

```bash
dpkg -s lypora | head -6                            # Status: install ok installed
dpkg -L lypora | wc -l                              # 文件数
```


## 使用注意事项

- **没有签名、没有软件仓库。** deb / rpm 都是无签名包，`apt install ./x.deb` 这种本地安装方式不校验签名；
  但如果你在强制 `AllowUnauthenticated: false` 或 `gpgcheck=1` 的环境里手工 `rpm -i`，会看到警告。
  也没做 `Packages` / `repodata`，所以不能 `sudo apt install lypora` 直接装——要先下 deb。
- **没有自动更新。** 升级 = 下新包覆盖（`apt install ./新.deb` 会原地升级，`dnf install ./新.rpm` 同理），
  AppImage 直接换文件，tar.gz 重跑 `install.sh`。
- **Linux 包这一版第一次在容器里真装过。** debian:12 与 fedora:40 两个容器里 `apt`/`dnf` 装、执行、
  查 setuid 全绿——但容器里没有 GPU、没有 D-Bus、没有真实桌面会话，**没有人在真实桌面上双击过它**。
  xvfb 冒烟只是尽力而为的一步，它成功不证明画面正确，失败也不代表包坏。
- macOS / Linux 包整体仍无真机运行记录（0.6.0 起就有这条，这一版没有改变它）。
- 项目是 **vibe coding** 产物：功能覆盖广，代码一致性一般，请当草稿看；遇到问题开 issue。

## New in this release

### 1. deb

`DEBIAN/` control files rendered from `packaging/debian/control.in`, the payload under `/opt/lypora`, a
three-line `usr/bin/lypora` shim, and the usual `/usr/share/{applications,icons,metainfo,licenses,doc}`.
`sudo apt install ./lypora_0.7.0_amd64.deb` and you get a menu entry and a `lypora` command; `postinst`
refreshes the desktop database and the icon cache so no logout is needed.

**The `a | b` dependency syntax is not cosmetic.** After Ubuntu 24.04's t64 transition, `libasound2` became
`libasound2t64`, `libatk-bridge2.0-0` → `libatk-bridge2.0-0t64`, `libcups2` → `libcups2t64`. A package naming
only the old ones installs on 22.04 and fails on 24.04 with missing dependencies. All three are declared as
`old | new`, which dpkg accepts and both LTS releases satisfy.

### 2. rpm

Same layout as the deb — that's the point of staging one tree: `%install` just `cp -a`s it. `__os_install_post`
and `debug_package` are disabled because Electron's binaries are already stripped; reprocessing them costs
minutes and buys nothing.

**The `chmod 4755 chrome-sandbox` at the end of `%install` must stay.** GNU `cp -a`, when run as a non-root
user, refuses to create a setuid file it cannot own — it quietly drops the s bit. `rpmbuild` normally runs as
an ordinary user, so the deb (built before any chown) was correct while the rpm installed as `0755` and died
with *"The SUID sandbox helper binary was found, but is not configured correctly"*. That single bit cost four
CI iterations; the trace is recorded as V48 in `docs/04`.

### 3. AppImage

No root, nothing written to system directories, uninstall = delete the file. The price is a **degraded
sandbox**: an AppImage has no root, so the SUID helper can never take effect and `AppRun` launches with
`--no-sandbox`. That's inherent to Electron-in-AppImage, not a misconfiguration — the UI and every feature are
identical; what's missing is OS-level isolation for renderer processes.

### 4. GitHub Actions: tag and it ships

`.github/workflows/linux-installers.yml` triggers on `push: tags: ['v*']` (or a manual run against an existing
tag): checkout → read version → `npm ci && npm run build` → fetch Electron v33.4.11 → stage the FHS tree →
tar.gz / deb / rpm / AppImage → structural checks (`dpkg-deb -I/-c`, `rpm -qip/-qplv`, `file`) → **install for
real in a `debian:12` container** → **install for real in a `fedora:40` container** → merge `SHA256SUMS.txt`
and `gh release upload --clobber` → optional `--selftest` under xvfb (best effort; timeout or failure does not
block the release).

**The container installs are the part that matters.** They don't unzip and eyeball a file list; they run
`apt install ./x.deb` / `dnf install ./x.rpm` through the real package manager, then assert four things: it
installed (`dpkg -s` / `rpm -q` succeed), files landed where they should ( `/usr/bin/lypora` executable),
**the setuid bit survived** (`test -u /opt/lypora/chrome-sandbox`), and it runs. That setuid assertion is
exactly what caught the bug above — `python tools/linux-stage.py` looks perfect locally; only a real install
reveals it.

`SHA256SUMS.txt` is **merged**, not overwritten: CI downloads the published list, strips the four names it is
about to replace, appends the new hashes and re-sorts. Windows / macOS / APK entries therefore survive a CI
re-run.

### 5. Other platforms

Windows, macOS and Android only take the version bump (`versionCode 8`); the code is that of 0.6.0. All five
builds carry the same `core/dist` — identical `index.html` sha256 prefix `c9beee20cc04`.

## Notes and caveats

- **No signing, no repository.** The deb and rpm are unsigned. Installing a local file with `apt install ./x.deb`
  doesn't check signatures, but a manual `rpm -i` under `gpgcheck=1` will warn. There is no `Packages` /
  `repodata` either, so `sudo apt install lypora` won't work — download the file first.
- **No auto-update.** Upgrading = install the new package over the old one (`apt install ./new.deb`,
  `dnf install ./new.rpm`), swap the AppImage, or re-run `install.sh`.
- **This is the first Linux release that has been installed for real**, inside `debian:12` and `fedora:40`
  containers — install, execute and setuid checks all green. But containers have no GPU, no D-Bus and no real
  desktop session, so **nobody has double-clicked it on an actual desktop**. The xvfb smoke step is best
  effort: passing doesn't prove the rendering, failing doesn't prove the package is broken.
- The macOS / Linux builds as a whole still have no real-hardware launch record (true since 0.6.0, unchanged).
- This is a **vibe coding** project: broad feature coverage, uneven code quality. Treat it as a draft, and open
  an issue when something breaks.

## 已知限制 / Known limitations

- Linux 包在容器里装过、跑过，但**没有在真实桌面会话里启动过**。
  The Linux packages were installed and executed in containers, but **never launched in a real desktop session**.
- 没有 arm64 包、没有 `dmg`、没有 Flatpak / Snap。arm64 只需给 `linux-stage.py` 一个 `--arch`，但没验过就不发。
  No arm64 package, no `.dmg`, no Flatpak/Snap. arm64 needs only an `--arch` flag — untested, therefore unreleased.
- deb / rpm 未签名，也没有软件仓库（不支持 `apt install lypora`）。
  The deb and rpm are unsigned and there is no repository, so `apt install lypora` is not a thing.
- macOS / Linux 包未在真机上启动过，只有静态结构证据 + 容器安装证据。
  The macOS / Linux builds have never been launched on real hardware — structural and container evidence only.
- Android 版未在真机上实测冷启动 / 原生读写 / 分享面板。
  The Android build has not been tested on real hardware for cold start, native I/O or the share sheet.
