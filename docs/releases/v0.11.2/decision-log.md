## 1. 为什么这次改动看起来小、实际上最容易做错

一行 CSS 挪位置，第一版在 1440px 下完全正确。到 900px 就叠字了。

### 1.1 故障链

三个默认值叠在一起，每一个单独看都合理：

| 元素 | 原写法 | 实际含义 |
|---|---|---|
| `.menubar-items` | `flex: 0 1 auto` + `min-width: 0` | 允许收缩，且**允许缩到内容宽以下** |
| 内部菜单按钮 | `white-space: nowrap` | 文字**不跟着盒子缩** |
| `.tabbar` | `flex: 1 1 auto` | 基准取内容宽（~635px），先占住再谈 |

于是：菜单盒被压到 300 多 px，里面的字仍按真实长度绘制 → 溢出自己的盒子 → 按绘制顺序盖在后画的
标签条上。同时标签条按 635px 基准撑开，两者把顶栏顶成 963px，横向溢出整个容器。

### 1.2 修法：给两条边定死角色

```css
.menubar-items { flex: 0 0 auto; }   /* 必须可读的那条：永不收缩 */
.menubar-right { flex: 0 0 auto; }
.tabbar        { flex: 1 1 0; }      /* 可滚动的那条：basis 0，吃剩下的全部 */
```

`flex: 1 1 0` 与 `1 1 auto` 的差别只在 basis，但在这里就是"能用"和"叠字"的差别：前者是"剩下多少我占多少"，
后者是"我先按内容宽占住"。**一条会滚动的东西要的是前者。**

窗口窄到放不下时，标签条在自己盒子里横滑（`overflow-x: auto`，滚动条隐藏），菜单一个像素不让。
900px 实测标签条可用宽 408px，三个标签照常切换。

### 1.3 为什么不能靠"看起来没问题"

因为**看起来确实没问题**——1440px 是设计稿的宽度，也是截图里的宽度。

## 2. 断言要加在哪：`scrollWidth` 才是真相

新增 `geometry/menu-tabs-one-row`，一次量四件事。第一版故障复盘时最重要的一条结论是：
**前三条在故障中全部通过。**

| 量什么 | 阈值 | 故障时 |
|---|---|---|
| 标签条内嵌于 `.menubar` | `parentElement` 相等 | ✅ 通过（结构确实对了） |
| 顶栏单行 | 高 ≤ 48px | ✅ 通过（确实 40px） |
| 菜单右沿到标签左沿 ≥4px | `rect` 相减 | ✅ 通过（盒子确实不重叠） |
| 菜单 `scrollWidth - width` ≤ 0 | — | ❌ **唯一能抓到的一条** |

盒子并排、高度正确、间隙为正，而盒子里的字比盒子宽。—— 这正是 `docs/04` V64「断言要测现象，
不测实现中间量」的第三次证明：`getBoundingClientRect()` 描述的是盒子，用户看到的是**字**。

顺手改掉一条过时的回归断言：`regression/tabbar-height`（整条标签条 30–38px）→
`regression/tab-item-height`（单个标签 39px）。标签条并排后高度由顶栏决定，量整条已经失去意义，
留着只会是又一个"恒真断言"。

## 3. 顺带修掉的 `--ce-top` 多算

排版面板顶边靠运行时量的 `--ce-top`：

```ts
// 旧：两段高度相加
const top = menubar.getBoundingClientRect().bottom + tabbar.offsetHeight

// 新：直接量结果的位置
const ws = document.querySelector<HTMLElement>('.workspace')
return Math.round(ws?.getBoundingClientRect().top ?? 0)
```

叠着的时候 40 + 39 = 79 是对的；并排之后这个式子仍然照算，面板被往下推 39px，上方漏出正文一条。

这不是"忘了改"，而是**"把组成加起来"这种写法本身的脆弱性**：它假设了两个块永远上下排列。
量结果的位置就没有这个假设。

## 4. 为什么是 0.11.2

不新增功能、不新增 API、不改数据格式。用户视角是"上面空了一点、正文多出两行"，回归视角是"67 条仍须全绿"。
补丁位。

没有做成设置项（"标签放上面 / 放旁边"）是刻意的：一个开关意味着两条布局路径都要长期维护、都要有断言、
都要在每轮改动后各验一遍，而用户要的只是"别浪费那一行"。
