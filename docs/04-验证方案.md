### 3.5 流畅度定量（`node tools/zoomperf.mjs`）

"不卡"不能靠肉眼说，用帧间隔对照测（同一台机器、headless Edge、120 帧）：

## 4. 踩坑记录（这是本文最有价值的部分）

### V1｜`@codemirror/language-data` 会拉几十个语言包

安装时 `ENOBUFS` 崩在 `lang-go` 上。该包依赖全部 legacy 语言包，对 Markdown 编辑器毫无必要。
**对策**：只装 `@codemirror/lang-markdown` + 自研轻量高亮器（`highlight.ts`，零依赖）。

### V2｜`package.json` 缺 `dependencies` 字段 → npm 互相裁剪

连续 `npm install <pkg>` 时，每次都会把上次装的包当"多余项"删除，表现出"装一个掉一个"。
**对策**：一次性把全部依赖写进 `package.json` 再 `npm install`。**永远不要连续单独装包。**

### V3｜`Block decorations may not be specified via plugins` ★架构级

CM6 明确禁止 ViewPlugin 提供块级装饰。我最初把表格/分割线/块公式全放进 ViewPlugin，结果：
页面抛 `RangeError`，且**表格、分割线、块公式、Mermaid 全部渲染失败**（连锁导致内部 `tile` 解构崩溃）。

**对策**：把装饰层拆成 `blockDecosField`（StateField，负责块级 widget）+ `livePreview`（ViewPlugin，负责行内与行装饰），用 `BlockState.covered` 协调，避免同一行被两个来源装饰。
**这一条决定了整个装饰层的架构，务必先理解再改代码。**

### V4｜`ListMark` 的父节点是 `ListItem`，不是 `OrderedList`

语法树层级是 `ListMark → ListItem → OrderedList/BulletList`（实测 `02` §3.3）。按 `parent.name === 'OrderedList'` 判断会把所有有序列表误判成无序，渲染成圆点。
**对策**：用标记文本首字符判定 —— `/^\d/.test(markText)` 即有序。

### V5｜滚动不产生事务 → 新进入视口的块没有装饰

`ViewPlugin.update()` 只在 `u.transactions.length > 0` 时重建，导致滚动后新进入视口的代码块露出 ` ``` ` 、标题露出 `##`。
**对策**：`update()` 必须响应 `viewportChanged`（以及 `docChanged / selectionSet / focusChanged`）。

### V6｜`resolveInner` 在空行上返回 `Document` → 专注模式全文档变亮

光标落在块间空行时，向上找到的"最外层块"是 `Document`，于是所有行都被判定为"活动"，一条都不变暗。

**对策分两层**：
1. 检测到 `Document` 时把当前块退化为**当前行**；
2. 当前行本身是空行时，向上（再向下）找最近的非空行，用那个块的 span —— 否则光标停在空行上会出现"全篇压暗、没有一处高亮"的怪状态。

实测（光标停在第 2 行空行）：`total 40 行，dimmed 39，唯一未变暗的是 H1 那一行`。

### V7｜编辑器内与 window 上重复绑定 `Ctrl+/` → 一次按键触发两次，等于没切

`EditorView.domEventHandlers` 返回 `true` 只阻止 CM 自身处理，**不阻止事件冒泡到 window**。
**对策**：应用级快捷键只在 window 上绑一次，编辑器内不再处理。

### V8｜`opacity: 0` 折叠的侧栏仍然 `isVisible() === true`

移动端侧栏是覆盖层，只改 `opacity` 仍会挡住正文点击。
**对策**：折叠态同时加 `visibility: hidden`。

### V9｜验证方法论：虚拟滚动让"数 DOM 节点"的断言全部失效 ★

CM6 只渲染视口内的行。在文档顶部去数 `.cm-table-widget`，永远是 0 —— 我因此误判了两轮"表格没渲染"。
**对策**：断言前必须先滚动到目标块。`verify.mjs` 里的 `scrollUntil(selector)` 就是干这个的：按 120px 步进滚动，找到目标元素后再回退一格。

> **推论**：这个工程不能靠"功能清单打勾"验收，必须靠"滚动到目标块 + 精确计数 + 截图人眼复核"三件套。

### V10｜菜单项文本含勾选号与快捷键 → 正则 `^Github$` 匹配不到

菜单项 DOM 是 `<span class=mi-check>✓</span><span class=mi-label>Github</span><span class=mi-shortcut>…</span>`，
`textContent` 拼出来是 `✓Github`。
**对策**：探针里按 `.menu-item` 的索引点击，或直接读 `.mi-label` 的文本，不要对整项 `textContent` 做锚定匹配。

### V11｜`[hidden]` 被 ID 选择器的 `display` 压过 → 切换 pane 时旧内容不消失 ★

侧栏切到「文件树」，大纲仍然显示。原因是 `#pane-outline { display: flex }`（ID 优先级 100）
压过了 `.pane[hidden] { display: none }`（类+属性 20）。
**对策**：`.pane[hidden] { display: none !important }`，并且**不要在 ID 规则里写 `display`**。
这条在 UI 层是通用陷阱：凡是用 `hidden` 属性做显隐，都要检查有没有更高优先级的选择器覆盖了 `display`。

### V12｜菜单根节点监听 `mousedown` → `element.click()` 打不开

为了避免与"点外部关闭"的 document click 抢跑，菜单根用的是 `mousedown`。
Playwright 的 `element.click()` 只派发 `click`，所以探针点了没反应，一度被误判成"菜单坏了"。
**对策**：一律用真实鼠标（`locator.click()`），或在探针里显式派发 `new MouseEvent('mousedown', {bubbles:true})`。
（和 V-任务复选框那条同源：**测交互要用真实事件序列，不要用 `element.click()` 代替**。）

### V13｜打包后 Electron 安全告警：缺 CSP

未设 `Content-Security-Policy` 时 Electron 会在控制台打红色警告，`--selftest` 的退出码因此变成 2。
**对策**：index.html 加 `<meta http-equiv="Content-Security-Policy">`，
放行 CM6/KaTeX 需要的内联样式与 `data:`/`blob:` 资源：
`default-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self' data:; frame-src 'self' blob: data:`。

### V14｜`ELECTRON_RUN_AS_NODE=1` 被父进程注入 → 主进程里 `ipcMain` 是 undefined ★

宿主（WorkBuddy 自身是 Electron 应用）会把 `ELECTRON_RUN_AS_NODE=1` 传给子进程。
此时 `require('electron')` 退化成"返回 exe 路径字符串"，解构出来的 `app/ipcMain/BrowserWindow` 全是 `undefined`，
报错是 `Cannot read properties of undefined (reading 'handle')`——看起来像代码写错，实际是环境问题。
**对策**：启动前剥掉该变量：`env -u ELECTRON_RUN_AS_NODE ./Lypora.exe`；
在 CI 或脚本里判断 `process.env.ELECTRON_RUN_AS_NODE` 并给明确提示。

### V15｜Electron 二进制在国内网络下装不下来

`npm i electron` 会走 GitHub Releases 下 110MB 的 zip，本机实测超时；`npmmirror` 的安装脚本同样失败。
**对策**：不用安装脚本，直接 `fetch` 镜像 + 系统 `bsdtar` 解压：

"/c/Windows/System32/tar.exe" -xf electron.zip -C desktop/node_modules/electron/dist

### V16｜rcedit 偶发 `Unable to commit changes`；且沙箱会拦删除操作

同一份 exe 连续改资源段时 rcedit 会报 `Unable to commit changes`（文件被占用/扫描）。
另外本环境的 `fs.rmSync`/`unlinkSync` 被安全钩子接管，删临时文件可能抛错或静默留下 180MB 垃圾。
**对策**：临时副本放**系统临时目录**（不要放产物目录），改完用 `copyFileSync` 覆盖回去，
清理失败也只记日志不中断——否则打包产物会莫名多出 180MB。

### V17｜在 `page.evaluate` 里滚动之后，键盘快捷键会"落空" ★

源码模式那一步加了"逐屏滚动累积文本"之后，紧随其后的 `Ctrl+/`（退出源码模式）失效了：
焦点不在编辑器上，快捷键没人接，于是**后续所有块级断言（表格、公式、分割线）全变成 0**，
看起来像"渲染坏了"，实际是测试脚手架把状态搞错了。

**对策**：任何 `evaluate` 改动滚动/焦点之后，恢复键盘操作前先 `.cm-content` 点一下；
并且在关键切换后**回读一次状态**（本例加了 `chipAfterExit` 断言），
不要假定"按了就是生效了"。

### V18｜Electron 里 `beforeunload` 会**静默**取消关窗（点叉号没反应）★

浏览器里 `beforeunload` 里 `preventDefault()` 会弹原生"离开此网站？"确认框；
**Electron 不弹，直接把 `close` 事件吞掉**——用户看到的就是"点右上角叉号关不掉程序"。

**对策**：关窗改成主进程单点负责，渲染层不再自己拦：

1. `win.on('close')` 里 `preventDefault()`，转入 `closeGuard()`；
2. 用 `webContents.executeJavaScript('window.__lyporaCloseState()')` 问渲染层是否脏；
3. 脏 → 原生三按钮对话框「保存并退出 / 不保存 / 取消」；
4. 选保存 → `executeJavaScript('window.__lyporaSaveAndClose()')`，
   返回 `ok:false`（用户取消另存为/写盘失败）就**留在窗口**；
5. 放行时置 `allowClose = true` 再 `win.close()`，并用
   `webContents.on('will-prevent-unload', e => allowClose && e.preventDefault())`
   压制渲染层残留的 `beforeunload`。

验收：`node tools/closetest.mjs [--exe]` 跑四场景（clean / cancel / discard / save），
用退出码 + 磁盘文件内容判定，不靠"看起来关了"。

### V19｜二级菜单"自食其尾"：鼠标一进子菜单就把它关掉 ★

给菜单加子菜单时，把"划到兄弟项就收起二级"的 `mouseenter` 挂在了**所有**普通项上，
而子菜单里的项也是用同一套渲染函数建的——于是指针进入子菜单项 → 触发兄弟判断 →
`closeSub()` → 子菜单当场消失，表现为"子菜单点不中"（Playwright 报
`element was detached from the DOM`）。

**对策**：`buildPop(items, sub)` 里用 `sub` 形参区分层级，兄弟收起逻辑只在
`!sub`（顶层下拉）时挂。**教训**：共用的渲染函数里，"当前层"的语义必须显式传进去。

### V20｜刚 `rename` 出来的 188MB exe 覆盖写会 `EBUSY`（Defender 扫描）

打包时把改好资源的临时 exe 覆盖回 `Lypora.exe`，偶发
`EBUSY: resource busy or locked`——文件刚由 `electron.exe` 改名而来，
Windows Defender 正在实时扫描。手工 `cp` 同一文件却成功，说明是**瞬时占用**。

**对策**：覆盖写重试 4 次、每次退避 1.2s；仍失败才降级为"图标保持默认"。
实测第 1 次重试即成功，产物版本信息 `0.3.0.0` 正常写入。

### V21｜单实例锁会把"另一个 Lypora 在跑"变成"新进程立刻退出码 0"

自测时发现 `--closetest` 全场景 `exit=0` 且没有任何日志：原因是上一次测试残留的
`Lypora.exe` 还活着，`app.requestSingleInstanceLock()` 让新进程直接退出。
**对策**：跑关窗/打包类验收前先 `taskkill /F /IM Lypora.exe`；
排查"启动即退"时先看有没有残留实例，别先怀疑代码。

### V22｜导入的 外部主题"完全没反应"——根因是两套契约不一样 ★

现象：从「主题 → 导入 CSS」选一个第三方主题，导入成功、菜单里也出现了条目、
localStorage 里也存下了，但**编辑区一个字都没变**。

根因不是导入坏了，而是原样注入必然空转，两个层面都不匹配：

| 层面 | 第三方主题写的 | 本项目 | 结果 |
|---|---|---|---|
| 选择器 | `#write h1`、`#write p`、`pre.md-fences` | 文档是 CM6 的 `.cm-line.md-line-h1` 等装饰类，**没有 `#write`、没有裸 `h1`** | 选择器一条都不命中 |
| 颜色 | `--bg-color`、`--text-color`、`--side-bar-bg-color`（参考实现变量） | 用 `--bg`/`--fg`/`--bg-side` | 变量全落空，只覆盖到无关变量 |

**对策**：加一层"主题适配"（`core/src/ui/theme-adapter.ts`），导入时做两件事：

1. **选择器转译**：`#write`→`.editor-host`、`h1`..`h6`→`.cm-line.md-line-hN`、`p`→`.cm-line.md-p`、
   `li`→`.cm-line.md-li`、`blockquote`→`.cm-line.md-quote-line`、`pre`→`.cm-line.md-code-line`、
   `a/strong/em/del/mark/code`→对应 `.md-*` 装饰类、表格/图片/公式→对应 widget 容器类；
   侧栏/大纲/搜索面板的选择器整段丢弃（本项目骨架不是参考实现那套 DOM）。
2. **变量桥**：把参考实现变量按优先级映射到本项目变量，缺的用 `color-mix()` 从主色推导，
   并单独处理"主题只给变量不给规则"的情况（很多主题 90% 的样式都在变量里）。

导入后 toast 会报"映射 103/133 条规则、34 个变量"这类统计，一眼能看出是不是真接上了。

### V23｜只保证"正文对比度"不够：深色侧栏 + 深色正文 = 1.42:1 不可读 ★

green-swiss 这类主题把侧栏做成深蓝 `--side-bar-bg-color:#003444`，而 `--text-color:#111`
是给米白纸张用的。适配层一开始把 `--fg` 直接喂给侧栏，结果侧栏**深底深字**：
实测对比度 **1.42:1**（正常文本要求 4.5:1）。同类问题还有状态栏（`--fg-muted` 落到浅底上 1.29:1）。

**对策**：骨架颜色按"区域"分别算，并做对比度守卫：

- `--fg-chrome*` 贴 `--bg`（菜单栏/状态栏），`--fg-side*` 贴 `--bg-side`（侧栏）；
- 候选值先测对比度，达标才用；不达标就按底色亮度自动取近黑/近白；次要文字用
  `blend(fg, bg, t)` 逐步向底色靠，直到刚好达标（保留层次又不糊）；
- `--control-text-color` **只能**当骨架文字候选，不能当文档次要文字色（它是给深色侧栏配的）。

验收口径也一并改了：以前只量正文对比度，现在每套主题都量 7 处骨架颜色（见 §3.3）。

### V24｜`mark` 映射到 `.md-mark` → 语法标记被涂成高亮块

本项目的 `==高亮==` 用 `.md-hl`，而 `.md-mark` 是"语法标记变淡"的类（`#`、`**` 这些）。
适配层最初把主题的 `mark{background:…}` 映射到 `.md-mark`，于是每个 `#` 号都被套上一个
圆角色块——每套主题颜色不同，看起来像是主题"渲染坏了"。
**对策**：`mark → .md-hl`。顺带把之前"设计了 `.md-hl` 样式但没人生成"的高亮补上：
段落里扫 `==…==`，分隔符变淡、中间加 `.md-hl`，光标落在里面时露出原文（与其他行内标记一致）。

### V25｜主题里的裸 `header`/`footer`/`aside` 会误伤界面骨架

我们的菜单栏/侧栏/状态栏恰好是 `<header>`/`<aside>`/`<footer>`，而 外部主题里
`header{background:…;color:#fff}` 这类规则是给它自己界面写的。放过去的结果是
green-swiss 出现"米白页面 + 深蓝菜单栏 + 白字"，看着像换了一半主题。
**对策**：只由裸骨架标签组成的选择器（无 id/无 class）整条丢弃；文档区里不存在这些标签，无副作用。

### V26｜`color-mix()` 的实算值是 `color(srgb …)`，正则解析会静默失败

对比度校验最初用正则解析颜色，`color-mix()` 派生出来的变量取到的是
`color(srgb 0.924 0.914 0.897)`，正则匹配不上 → 函数返回 `null` → 断言直接记 0 分，
表现为"所有主题骨架全 0 分"的假失败。
**对策**：浏览器里用 1×1 canvas 归一化（`fillStyle = 任意颜色 → getImageData`），
Node 侧只处理 `r,g,b` 三元组；适配层内部也补了 `color(srgb …)` 解析。

### V27｜CSS 嵌套之后 `CSSStyleRule` 也有 `cssRules`，按"有没有子规则"分支会漏掉一切

排查 V24 时写的"找出命中元素的所有规则"探针，写成
`if (r.cssRules) { walk(r.cssRules); continue }`，结果每条样式规则都带一个空的
`cssRules`（CSS Nesting 之后的新行为），于是 `selectorText` 永远没被检查，返回空列表，
白排查了一轮。
**对策**：先判 `selectorText`，只有没有选择器的（`@media`/`@supports`）才递归。

### V28｜`pointerdown` 里 `preventDefault()` 会掐掉整条兼容 mouse 事件链 ★

表格列宽分隔线做完后，「双击均分」怎么点都没反应。

**根因**：拖拽起点为了不让 CodeMirror 抢焦点、不让浏览器起选区，在 `pointerdown` 里调了
`preventDefault()`。按 Pointer Events 规范，`pointerdown` 被取消后浏览器**不再派发**兼容的
`mousedown`/`mouseup`/`click`/`dblclick`——所以 `dblclick` 监听器永远不会触发。

**对策**：自己识别双击（`pointerup` 时位移 ≤3px 且距上次 ≤350ms 即算双击），别再依赖 `dblclick`。
同一处还有第二个坑：`pointerdown` 上的 `stopPropagation()` **拦不住** `mousedown`（两者是独立派发的
事件），而表格 widget 在 wrap 上挂了 `mousedown` → 光标跳表首 → 表格塌回源码态，所以分隔线必须
自己再吃掉一次 `mousedown`。

### V29｜字号平滑的真源是 CSS 变量，不是 `EditorView.reconfigure`

**现象**：改造前只有整数档位（一次 1px 硬跳）；若用 `view.dispatch` 换主题来改字号，每滚一格
都要重建整个编辑器，滚起来一卡一卡。

**做法**：`EditorView.theme` 里 `fontSize` 写的是 `var(--content-font-size)`，所以滚轮只需要
`setProperty` —— 浏览器做一次样式重算 + 重排，编辑器实例完全不动。再加三条：
① rAF 合并（滚轮事件可达 120Hz，逐事件写样式会重复重排）；
② `deltaMode` 归一（LINE→×16、PAGE→×`window.innerHeight`）；
③ **滚完 300ms 才写 localStorage**——同步 IO 是滚轮掉帧最常见的来源。

**另有一个必须拦的东西**：Chromium 自带 `Ctrl+滚轮 = 整页 zoom`，会和"调字号"叠加成"界面整体忽大
忽小"。渲染层要 `capture + passive:false` 抢先 `preventDefault`，主进程再监听 `zoom-changed` 把
`zoomFactor` 复位、`setVisualZoomLevelLimits(1,1)` 关掉触控板捏合，两层都拦住才干净。

### V30｜表格列宽存"比例"不存"像素"，且必须与 Markdown 源码解耦

参考实现拖列宽不改源码（`| --- |` 只有对齐信息，没有宽度），所以列宽属于视图状态：
按「表头文本 + 列数」生成签名存 localStorage，改表头/改列数就自动回到默认布局。

存的是**比例**（和为 1）而不是像素：正文宽度、窗口大小、字号变化后仍按同样比例分配，不会出现
"窗口一拉宽列宽就错乱"。渲染侧用 `<colgroup><col>` 做列宽真源；拖动开始前先把当前像素宽快照成
比例、再切 `table-layout: fixed`——不切的话 auto 布局会让别的列跟着内容一起跳。

窄列换行要用 `overflow-wrap: break-word`，**别用 `anywhere`**：后者会把 `12.5`、`2026-10-23`
从中间拆断。

### V31｜拖拽产生的「全局状态」必须在 `destroy()` 里兜底，`pointerup` 不一定来

**现象**：按住分隔线拖动时按 `Ctrl+/` 切到源代码模式，表格 widget 被销毁，
`pointerup` 再也不会派发到那个 grip 上。于是 `document.body` 上的 `col-resizing`
永久残留——整页光标都变成 `col-resize`，切回预览态也不恢复。

**对策**：把全局副作用（`body.classList`、`document.body` 级样式）的回收写进
`WidgetType.destroy(dom)`，不要只依赖 `pointerup`/`pointercancel`。
同时约定：**被中断的拖动不落盘**（`pending` 只在正常 `pointerup` 且位移 > 3px 时才 `saveColRatios`），
所以中断后再回到预览态，列宽应当回到上一次成功保存的值。

验收方式：`probe5` 断言 `afterSource = { body: "", cursor: "auto", grips: 0 }`。

### V32｜"流畅"必须分三段测，否则会把测量开销算到自己头上

**现象**：直觉写法是"滚一轮，量帧间隔"。第一次测出来 p50 18.9ms（基线 16.7），
看着像自己的代码慢了 2ms。但把一轮 `wheel` 拆成三段对照就发现，**事件派发是免费的**：

| 场景 | p50 | p95 | 结论 |
|---|---|---|---|
| 什么都不做（基线） | 16.7 | 16.8 | 这台机器的噪声底 |
| 同款 `WheelEvent` 但不按 Ctrl（处理器第一行 return） | 16.7 | 16.8 | 派发本身 0 成本 |
| Ctrl + wheel（真的改字号） | 18.1–19.0 | 31–35 | 增量全部来自"改字号 + 重排" |

也就是说，那 1.4–2.3ms 是**每帧重排整篇文档**的实价：`--content-font-size` 一变，
行高全变 → CM6 的 `ResizeObserver` 触发 measure → 遍历视口内每个块重新量。
文本编辑器逐帧改字号绕不开这一步，除非改用 `transform: scale` 作弊（代价是整个手势期间
文字发虚），所以这里如实保留 2ms 级开销，而不是假装零成本。

**判定标准也随之改成有原理依据的三条**，而不是"p95 必须 16.7"（那是做不到的）：
① 每帧重排开销 ≤ 一帧预算的 18%；② 无 longtask（>50ms 阻塞）；③ 任一帧停顿 ≤ 2.4 个 vsync
（最多丢一帧，不连丢）。工具：`node tools/zoomperf.mjs`。

**顺带排除了另一个假优化**：把变量改到 `.editor-host` 上（缩小样式失效范围）实测毫无改善
（23.3 vs 23.2，噪声内），说明全文档样式重算并不是瓶颈，CM6 的 measure 才是——所以维持
写在 `documentElement`（导出与自检都读这一处，改了反而要同步三处）。

### V33｜分隔线位置不能靠 `ResizeObserver` 自动跟，得主动吸附 ★用户实测发现

`grip` 是绝对定位在 `.cm-table-stage` 里的独立元素，位置靠 `cell.right - stage.left` 算出来。
最早的实现只写了 `ro.observe(table)`，结果有两个地方必错：

**① 拖动时高亮线不跟手。** 拖列宽只重分配相邻两列，**表格总宽恒定不变** → `ResizeObserver`
根本不会触发 → `left` 一直是按下时的旧值。实测左列已经到 284px，分隔线还停在 213px，
偏差 71px；松手也不修正。修法：`onMove` 里每次 `setRatios` 之后同步调一次 `syncGrips()`。

**② 换主题 / 改字号之后整体错位。** 主题改了表头 padding、字号变了文字宽度，都会让各列
重新分配宽度，但总宽仍是 `width:100%` → 同样观察不到。实测换主题后错位 9px。修法：
`ro.observe(table)` 之外**把每个 `th` 也 observe 一遍**（th 的宽度变化必然触发）。

**验收**：`verify.mjs` 第 14 步新加 4 项断言，直接比对每条 `grip.style.left` 与
`th.getBoundingClientRect().right - stage.left` 的差，要求 ≤1px：
初始 `[0,0]`、拖动中 `[0,0]`、刷新后 `[0,0]`、自动布局改字号后 `[0,0]`
（最后一组同时要求列宽真的变了：`[212,472,175] → [207,484,168]`，总宽 `860 → 860`，
否则断言会退化成"没变所以对齐"的假通过）。

**触摸端另测过**：`@media (pointer: coarse)` 把命中区从 11px 放大到 22px，
真实触摸事件（CDP `Input.dispatchTouchEvent`）拖动有效（`194 → 274px`），
页面滚动位置不变（`touch-action: none` 生效）。

### V34｜导出的 HTML/PDF 里公式散架：KaTeX 的 HTML 是骨架，排版与字体在 CSS 里 ★用户实测发现

现象：编辑器里公式正常，但「导出 HTML」和「导出 PDF（打印）」出来的公式变成
`∫ − ∞ ∞ e−x2 dx = π` 这样一串平铺文字，还带一条横向滚动条和一个游离的 `√`。

**根因**：`katex.renderToString(..., { output: 'html' })` 只输出**结构**：

```html
<span class="katex-display"><span class="katex"><span class="katex-html">
  <span class="base"><span class="strut" style="height:2.38em;vertical-align:-0.97em"></span>
  <span class="mop"><span class="mop op-symbol large-op">∫</span><span class="msupsub">
  <span class="vlist-t vlist-t2">…</span> …
```

上下标之所以能「堆」起来，靠的是 `.vlist>span{position:absolute}`、`.strut`（撑高）、
`.sizing/.reset-size6`（缩放）、`.pstrut`（伪基线）这一整套 CSS，外加 20 个
`KaTeX_*` 字体（度量决定积分的上下限位置、根号的横线长度）。缺一样就退化成顺序文本。

应用里没这个问题，因为 `src/editor/math.ts` 里 `import 'katex/dist/katex.min.css'`，
样式由 Vite 打进主 bundle 全局生效。**但导出物是独立文档**：`buildHtmlDocument()`
自己手写了一份 `<style>`，里面只有 `.katex-display{margin}` 这种零星规则，
KaTeX 的布局 CSS 和字体一个都没跟过去。

实测导出文件里 `katex` 只出现 3 次（全是 class 名），`@font-face` 0 个、`KaTeX_*` 0 个。
HTML 和 PDF 两条路用的是**同一份** `buildHtmlDocument()` 输出，所以两者同时坏——

- **触发条件（HTML）**：文档里含公式，且用「导出 HTML」导出。双击打开就坏，与浏览器无关。
- **触发条件（PDF）**：同样含公式，且用「导出 PDF（打印）」。PDF 还多一层依赖
  —— 打印时字体必须已经就位（见 V35），否则即使 CSS 齐了也会印出回退字体。

**修法**：`core/scripts/gen-katex-css.mjs` 在构建前把 `katex.min.css` 里的
每个 `@font-face` 收敛成「单个 woff2 的 `data:` URL」（丢掉 woff/ttf 兜底），
生成 `src/io/katex-inline.ts` 里的 `KATEX_CSS` 常量（20 个字体，约 360KB），
`buildHtmlDocument()` 在正文含 `class="katex"` 时把它整段塞进导出文档。
CSS 排在我们的主题规则之前，所以主题仍能覆盖 margin 之类的外层样式。

**别忘反向断言**：纯文字文档不该白白背上 360KB。实测含公式导出 382KB、
不含公式 4KB，两个数字都进了断言，防止以后有人图省事无条件内联。

**顺带修正**：`.math-block{overflow-x:auto}` 在打印时会带出一条横向滚动条（用户截图里
那条灰条就是它），`@media print` 里改成 `overflow:visible` + `break-inside:avoid`。

### V35｜打印 iframe 不能给 0×0，且必须等 `document.fonts.ready` 再 print()

`exportPdf()` 原先用 `width:0;height:0` 的隐藏 iframe 承载文档。两个问题：

**① 0 宽排版。** iframe 内部的布局宽度是 0，`.math-block`、`pre` 这些带
`overflow-x:auto` 的块会溢出 —— 实测 `scrollWidth - clientWidth = 153px`，
打印快照会把这条滚动条一起印进 PDF。改成按 A4 可打印宽度
（`210mm - 16mm×2 ≈ 672 CSS px`）、高 1123px，再用 `position:fixed; left:-20000px` 移出视口。

**② 字体没就位就打印。** 之前是 `iframe.onload` 或 900ms 兜底直接 `print()`。
KaTeX 用字体度量算 `.strut` 高度和上下标位置，字体没加载完时版面是「按回退字体算好的」，
打印出来的公式会偏。改成 `await document.fonts.ready`（3s 上限）后再等两帧，
让度量重排落进打印快照；`openInNewWindow()` 的兜底路径同样处理。

**验收**：`core/export-check.mjs` 四条路径全绿（屏幕态 / 打印媒体 / 真 PDF / 打印 iframe），
`tools/pdfexporttest.mjs` 在**打包版**里把 iframe 的 `contentWindow.print` 换成桩，
断言打印确实被调用（`printCalled: 1`）且框内 `.katex` 的
`font-family` 首位是 `KaTeX_Main`、`.vlist-t` 是 `inline-table`、
`fonts.check('16px KaTeX_Main')` 为真、块高 3.68em（上下限真的堆叠）、溢出 0。
PDF 用 `page.pdf()` 出真文件后，`pymupdf` 读字体表可看到
`KaTeX_Main-Regular / KaTeX_Math-Italic / KaTeX_Size1-Regular / KaTeX_Size2-Regular`，
把第 2 页渲成 PNG 肉眼复核，积分上下限、根号罩住 π 全部正确。

### V36｜`cap copy` 不清旧 hash 文件，APK 里打进了上一版样式

前端产物是带 hash 的文件名（`index-CadlbVGF.js` → `index-DCmq_ejv.js`）。改完代码重新 build 后，
`npx cap copy android` 只负责「复制过去」，**不会删掉上一次留下的旧文件**；而 `index.html` 已指向新名字。
如果 copy 恰好在某个文件被 Gradle 进程占用时异常退出（CLI 只打一行栈就继续了），
`assets/public` 就会停在上一个版本 —— 表现是**本地 `vite preview` 完全正常，装到手机上是旧界面**。

**判据**：不要看目录里有没有新文件，要比**文件名集合 + 每个文件的 SHA256**。
`tools/build-android.mjs` 现在的流程是 `rm -rf assets/public` → `cap copy` → 逐文件哈希比对 →
`gradlew`，任一步不一致直接非零退出。

### V37｜`z-index:-1` 的伪元素遮罩会把面板自己压暗；合并的 `display:none` 会把它变成隐身

菜单面板最早用 `.sheet::before { position:fixed; inset:0; background:rgba(0,0,0,.34); z-index:-1 }`
当遮罩。实测截图里**面板自身也变灰**（负 z-index 子元素在 .sheet 的层叠上下文里排在背景之上），
而且容易连带改到别的层。改成两个兄弟节点：`.sheet-backdrop`（z 119）+ `.sheet`（z 120），层级一眼可见。

顺带一个坑：基础规则里写了 `.mobile-dock, .drawer-scrim, .sheet, .sheet-backdrop { display:none }`，
后面只给 `.sheet-backdrop` 补 `position/background` 是**不会显示**的 —— 必须在同一规则里显式
`display:block` 覆盖。第一次改完遮罩没出现，就是这个原因。

### V38｜Android 构建的 JDK 必须 21：17 与 25 都不行

- JDK **25**（本机默认）：Gradle 8.11.1 直接起不来。
- JDK **17**：Gradle 能起，但编译 Capacitor 插件时失败 ——
  `@capacitor/filesystem`、`@capacitor/share` 的 `build.gradle` 声明了
  `toolchain languageVersion=21`，报 `Cannot find a Java installation … languageVersion=21`。
- JDK **21**：通过。

`tools/build-android.mjs` 会按 `JAVA_HOME` → `lypora-toolchain/jdk-21` → 常见安装路径 顺序探测，
要求主版本 ≥21，并把自己选中的路径打出来，避免"到底用的哪个 JDK"这种扯皮。
